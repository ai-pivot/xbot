## Gotchas — MUST READ Before Any Code Change

### Concurrency
- **Loop breaker（iteration-loop detection）默认关闭（实验开关，2026-08-31 起）——必须在 config.json `agent.experimental.iteration_loop_detection: true` 显式开启。** 接线：`config.ExperimentalConfig.IterationLoopDetection` → `server_core.go` 传 `agent.Config.IterationLoopDetection` → `Agent.iterationLoopDetection` → `buildMainRunConfig`/`buildSubAgentRunConfig` 填 `RunConfig.IterationLoopDetection` → `newRunState` 初始化 `runState.loopDetectionEnabled`。`detectIterationLoop` 开头 gate（`s.loopDetectionEnabled && ...`）：关闭时不置位 `loopDetected`（拦截/loopBreakCount/loopFatal 全链路休眠），但**签名追踪（lastIterSignature）照常更新**（无状态、开销为零，开关切换即时生效）。开启后的行为（下述）不变。**Loop breaker 绝不插入 user message —— 重复调用被替换成挂真实 tool_call_id 的 fake tool result。** `detectIterationLoop` 检测到连续迭代 content+tool_calls 逐字节相同时只置 `runState.loopDetected`；`executeToolCalls` 据此走 `fakeLoopToolResults`：**不执行重复工具**，为每个 tool_call 构造 `Error: ⚠️ LOOP DETECTED` 的 tool result（配对 assistant 的真实 tool_call_id → SanitizeMessages 保留 → LLM 下一迭代看到警告）。旧实现直接 append `Role:"user"` 假消息 → 增量持久化进 DB（role=user, turn_id=当前 turn）→ web 前端按 (turnID, role) 分组渲染时**假 user 行顶替用户真实消息**（用户报告的严重 bug）。fake result 的 `err==nil`（`lastIterHadError` 不置位）→ 模型无视警告继续重复时持续拦截；上一迭代真实工具报错则不拦截（重试合理）。Test: `TestDetectIterationLoop_DisabledByDefault`（默认关闭不拦截）+ `TestDetectIterationLoop_ReplacesDuplicateCallsWithFakeToolResult` 等 4 个开启路径测试（构造 runState 时显式 `loopDetectionEnabled: true` / RunConfig `IterationLoopDetection: true`）。
- **Never `defer` semaphore release inside a loop.** Deadlock when iterations exceed capacity. Release immediately after Generate completes.
- Non-blocking channel sends: always use `select` with `ctx.Done()` to prevent blocking on full channels during shutdown.
- **User-scoped semaphores must not be hardcoded to capacity 1 when one sender can own multiple independent chats/sessions (for example remote CLI windows authenticated as `admin`).** Size them from configured concurrency or key them by session, otherwise different windows will block each other and look like a leaked semaphore.
- **`SetMaxConcurrency` must clear `userSemaphores` cache.** The global semaphore is rebuilt with the new capacity, but `getUserSemaphore` caches per-user channels in a `sync.Map` via `LoadOrStore`. Without `Clear()`, users with custom LLM keep using the cached semaphore with the OLD capacity forever. Symptom: setting max_concurrency to 100 has no visible effect.
- **⛔ `max_concurrency` 只能有一个存储位置（2026-09-17 用户报告根治）：「设了 100 并发，只起 4-5 个子代理就卡」+「统计里的 TTFT 很短、和入库时间对不上」。** 当时同一个设置在 **4 处**各存一份、且**读路径按调用方 channel 读**：① `config.json` `agent.max_concurrency=7`；② `AGENT_MAX_CONCURRENCY` 环境变量；③ `user_settings` **多行**（CLI 面板写 `channel='cli'`、Web LLM 控制台写 `channel='web'`、老代码写 `channel=''`）；④ 兜底 `llm.DefaultLLMConcurrency=5`。而 `LLMFactory.LLMSemAcquireForUser(senderID, **channel**)` 用**调用方 channel** 读该键 ⇒ web/feishu 会话读不到行 ⇒ **静默退回 5**（面板还显示 125）。**唯一权威 = `user_settings` 规范行（`channel.MaxConcurrencyChannel`='cli' + sender `cli_user`）**：新增 `channel.MaxConcurrencyChannel` / `channel.SettingMaxConcurrency` 常量；`SettingsService.SetSetting` 对**该键**强制规范化 channel（单一写入收口，任何写入方都落一行）；`LLMFactory` 两个 acquire（`LLMSemAcquireForUser` / `SubAgentSemAcquireForUser`）改读规范 channel（忽略调用方 channel 形参）；**删除重复定义**：`config.AgentConfig.MaxConcurrency` 字段 + `AGENT_MAX_CONCURRENCY` env + config.json 回写（`saveServerConfig`）+ `set_llm_concurrency` 里的 cfg 镜像 + `get_settings`/CLI 的 config 兜底注入；`subagent_max_concurrency`（重复旋钮）删除，子代理共用同一上限；启动时 `serverapp/server_core.go` 在 `agent.New` 之后 `ag.SetMaxConcurrency(ag.GetLLMConcurrency())`（DB 为准）。**老数据迁移**：`migrateV67ToV68`（`storage/sqlite/migrations.go`，schemaVersion **68**）把该键的多行合并成唯一规范行（规范行优先；缺失则取最新值提升；其余删除；幂等），禁止"一份数据到处跑"。Tests: `agent/llm_factory_test.go`（`TestLLMSemAcquireForUser_IgnoresCallerChannel`：caller='web'/'feishu'/'' 仍取规范值 100；`TestSetSetting_CanonicalizesMaxConcurrencyChannel`）+ `storage/sqlite/migration_v68_test.go`（3 行→1 行 / 规范行缺失时提升最新值 / 幂等）。
- **⚠️ 排查"TTFT 很短但体感很慢"必须知道：排队时间不计入 TTFT。** TTFT 基线 = `generateResponse` 发起前（`agent/engine_run.go:750-752`、`:931-933` 的 `ResetStreamTiming` + llm 层 `RetryLLM.GenerateStreamAndCollect` 的 acquire 之后、`GenerateStream` 之前取 t0），而**信号量/并发闸门的等待发生在 t0 之前** ⇒ 等 30s 拿到槽位 + 0.6s 首字 = **面板显示 0.6s**。判断"卡在哪"的正确方法：拿 `iteration_history` 的**相邻两行 `created_at` 差值**减去该迭代的 `total_ms` 与工具耗时（`tools` JSON 的 `elapsed_ms` 之和）——剩下的"未解释间隔"就是排队/引擎侧开销，不是 LLM。
- **`cancelChildSessions` must only cancel sessions with matching `parentKey`.** The old code called `cancelCurrent()` on ALL interactive sessions inside the `Range` loop before checking `parentKey`. This killed sibling/peer background agents when any single agent was unloaded or panicked — all N peer agents die simultaneously at whatever time the first one finishes. The `parentKey` check must happen BEFORE `cancelCurrent()`.
- **SubAgents must never outlive their direct creator — ALL completion paths need `cancelChildSessions`.** Foreground SubAgents wrap their own `fgRunCtx` (with `bgSessionCtxKey`+`bgParentKey`) so children derive context from the creator, not a grandparent. Send path `runCtx` also has these markers. Every natural completion path (foreground, bg, send) calls `runCancel()` + `cancelChildSessions(key)`. Without the context wrapper, a foreground B creating bg C would have C's context chain skip B entirely → B finishes, C keeps running.

### Subscription & Settings
- **Multi-user system REMOVED (v63): single operator + admin allowlist.** The canonical user layer (users/user_identities/link_codes tables, IdentityResolver, owner_user_id columns) was deleted. There is exactly ONE operator: `ResolveUserContext` collapses every sender to the fixed operator identity (`cli_user`) — subscriptions, settings, workspace, memory are GLOBAL. Admin rights come from `Agent.isAdminSender(channel, senderID)`: `cli`/`web` channels are always admin (local operator / password login), every other channel (feishu/qq/...) requires the senderID in `config agent.admins`. `RunConfig.OriginUserIsAdmin` is the precomputed decision consumed by the tool layer.
- **Management commands and tool actions are operator-gated.** `protocol.CommandInfo.AdminOnly` + `commandRequiresAdmin` gate both dispatch points (processMessage + chatWorker): `/set-llm /unset-llm /llm /llms /models /set-model /settings /usage /plugin /app` reject non-admin senders. The config tool's `model/subscription/runner/reload_*` actions and ManageTools' `add_mcp/remove_mcp/reload` check `ctx.OriginUserIsAdmin`. Conversational commands (`/new /compress /goal /info /export /bang`) stay open.
- **DB v63 migration** (`migrateV62ToV63`, tests in `storage/sqlite/migration_v63_test.go`): UNIQUE conflict resolution (operator's row wins) → sender collapse to `cli_user` (incl. `user_llm_subscriptions.sender_id` — the `List()` query dimension) → token usage SUM-merged → xbot memories `user_id=1` (column KEPT — memory scopeWhere reads it) → DROP canonical columns (`user_llm_subscriptions/user_settings/user_default_model/user_chats/cron_jobs/event_triggers .user_id`, `tenants/runners .owner_user_id`; `idx_cron_jobs_user` dropped first) → DROP `users/user_identities/link_codes`. Every step guarded by `tableExists` (hand-built migration-test fixtures may lack tables) + `HAVING COUNT(*)>0` on token-usage aggregates (empty set emits a NULL row violating NOT NULL).
- **`Agent.ResolveUserContext` is the SINGLE boundary between the (removed) user system and the agent loop.** It resolves LLM/settings/sandbox/concurrency components once at `processMessage` entry, carried via `context.Context` (`WithUserContext`/`UserContextFromContext`). The admin decision (`isAdminSender`) runs on the ORIGINAL channel+sender BEFORE the operator collapse. **NEVER access `a.llmFactory`/`a.settingsSvc` directly in agent loop code** — read from `UserContext` closures (`uc.SubSvc`, `uc.SettingsSvc`, `uc.ResolveLLM(chatID)`, `uc.SelectModel(chatID, subID, model)`, `uc.RefreshModels()`, `uc.InvalidateLLM()`, `uc.HasCustomLLM()`).
- **`agent/setting_runtime.go` is the SINGLE source of truth for runtime setting handlers.** Both CLI and server use it. Never create a second handler registry — it will silently diverge.
- **`backendSubscriptionManager` is the SINGLE SubscriptionManager implementation.** No more local/remote/config variants. All subscription operations go through Backend interface → Transport (local or remote).
- **⚠️ Web 端 LLM 配置必须「两边数据统一」：设置里改完，会话 LLM 选择栏必须立刻更新（用户报告 2026-09-16：「设置里添加/更新 LLM 之后，当前会话的 llm 选择栏不更新，需要刷新」）。** 根因：`useLLMSettings()` 有**两个独立实例** —— `AgentPanel`（喂会话 LLM 选择栏 `ModelSelector` 的 `subscriptions`/`modelEntries`）与 `SettingsDialog`（做订阅/模型增删改），两个实例各持 state，**所有 mutation 只 `await load()` 自己那份**（只有 thinking mode 有跨实例总线 `thinkingModeBus`）⇒ 设置里加完订阅，选择栏那份数据仍是旧的，必须刷新页面。修复：`useLLMSettings.ts` 新增**模块级 LLM 配置变更总线** `llmConfigBus`（+ 导出 `subscribeLLMConfigChanged`），**每处 mutation 成功后 dispatch**（订阅 CRUD / 模型 upsert·remove·enable·per-model / refreshModels / tier），每个实例监听到**非自己 origin**的事件就 `void load()`（origin = 每次 `useLLMSettings()` 的稳定 instance id，避免触发方重复拉取）；`AgentPanel` 另订阅同一总线 → `sessionContext.refresh()`（当前模型/上下文上限也要重解析）。**契约：任何"改服务端 LLM 配置"的新写入口都必须 dispatch 这条总线**（否则又会分叉）。Tests: `web/src/hooks/useLLMSettings.sync.test.ts`（两实例：dialog 加/改订阅 → bar 实例必须同步看到，修复前全红）+ `web/e2e/llm-settings-sync.spec.ts`（真实浏览器：设置里加订阅 → 关闭弹窗 → 会话选择栏弹层立刻出现新订阅+新模型，全程不刷新）。**E2E 坑**：断言必须限定在弹层容器内（`[data-radix-popper-content-wrapper]`），否则会被 "Added …" toast 命中造成假阳性；且必须注入保持连接的 mock EventSource —— `useLLMSettings.load()` 在 `!connected` 时**直接跳过拉取**，SSE 断开会让验证假失败。
- **Never use `UpdateSubscription` for PerModelConfig changes.** Use `UpdatePerModelConfig(subID, model, pmc)` — it only touches PerModelConfigs, never touches credentials. The old List→modify→Update pattern reads masked keys from the API, then writes them back, destroying real credentials.
- **`serverapp/rpc_table.go:updateSubscription` starts from EXISTING subscription, only overlays non-masked fields.** Client sends masked keys (****) — the handler preserves real credentials from DB.
- **⛔ 模型解析严禁用"裸模型名"——任何时候解析模型必须带订阅 id（用户明确要求，2026-09-11）。** 唯一被接受的"具体模型"形式是 **`<subID>|<model>`**（tier 值本来就是这种 pair）；`ResolveSubscriptionForModel`（按模型名反查提供者）**已整体删除**，`GetLLMForModel` 的 bare-name 分支也已删除（裸名 → 明确报错日志 + 回落会话/部署默认，绝不猜）。原因（真实数据）：同名模型常同时挂在多个订阅下 —— `glm-5.3` 在 mint(1M)/mintcn(0)/openai mint(0) 三处都有行、`deepseek-flash` 在 dpsk(0)/dpsk mint(1M) 两处都有行；按名找订阅**必须猜**，猜错就把别的订阅的 per-model 配置（max_context=0）当成该模型的配置 → 上层 `applyUserContextLimits` 静默回落 agent 级全局 200k（用户症状：设置里 1M、子代理只有 200k，且 mask/压缩阈值由 maxTokens 推导 → 表现为"mask 对子代理有 bug"）。**也不允许"按模型名挑配置更全的订阅"这类启发式**（同样是按名解析，只是挑得更聪明 —— 属 hack，已撤销）。调用方（SubAgent model/角色 model、CreateChat model、tier 值）必须传 pair；缺 subID 时拒绝覆盖并使用已配置的默认绑定，不猜。Test: `agent/model_pair_resolution_test.go`（裸名不解析 / 显式 pair 解析并带上该模型自己的 max_context）。
- **`max_context_tokens` is per-model, NOT per-subscription.** Stored in `PerModelConfigs[model].MaxContext`, NOT in user_settings DB or config.Agent.MaxContextTokens. `/settings` writes only the current session's model via `UpdatePerModelConfig`, preserving existing `MaxOutputTokens`. The old `SetMaxContextTokens` / `set_max_context_tokens` RPC / `perChatMaxCtx` map / `max_context_tokens` setting handler have all been REMOVED — settings writes go directly to DB via `UpdatePerModelConfig`, and `GetEffectiveMaxContext` reads from DB via `resolveSubContextFor`. Must NOT pass `max_context_tokens` to `ApplySettings` — there is no handler for it anymore.
- **⚠️ 会话模型绑定永不留空 + 单 operator user_default_model 兜底（2026-09-07 "模型漂移 + 显示 1M 但 200k 触发压缩"根治）。** 用户报告三连 bug 的同一根因链：**(a) `ensureSessionModel` 的"已绑定"判定只查 `subID != ""` 不查 model** —— tenants 表 (subID, model='') 的毒化绑定永不修复，`ResolveLLM` 每次走 `if model == ""` 的 `GetLLM` fallback → **会话模型跟随 user_default_model 漂移**（别的会话 SelectModel 更新 last-used → 本会话模型变了，"用户没切换模型但模型变化"）+ **压缩阈值分裂**（显示链 ResolveContextConfig 读 tenants 的 (sub,model) 得 per-model 1M，压缩链 ResolveLLM 漂移到 user-default 链的模型/全局 defaultModel → 无 per-model 配置 → userMaxCtx=0 → applyUserContextLimits 回退 config 200k → "显示 1M 但 200k 触发压缩"；生产日志铁证：web:chat_FE5FFB8AC961 need=true max_context=200000，同会话 tenants 绑定 glm-5.3-fp8 per-model 1M）。**(b) 空 model 写入源**：`SetSessionLLM` 用 `user_default_model` 的 Model（可空）写 tenants + `setDefaultSubscription` RPC 直写 `sub.Model`（DB 里订阅 Model 列全空！）→ tenants.model='' 行（生产 DB 有 3 条 CLI 会话证据）。**(c) `GetUserDefaultModel('cli_user')` miss**：v63 只折叠了 user_llm_subscriptions 的 sender，`user_default_model` 表残留 pre-v63 sender 行（生产 DB：sender_id='web-4'）→ GetLLM 链 fallback 到 config defaultModel。**修复四件套**：① `GetUserDefaultModel`（storage/sqlite/user_llm_subscription.go）单 operator 兜底 —— 精确 sender 行 miss 时读最新行（`ORDER BY updated_at DESC LIMIT 1`）；② `ensureSessionModel` 判定改 `subID != "" && model != ""`（空 model 视为未绑定）+ 4 级 fallback 链：balance tier → user_default_model（last-used）→ 已绑定订阅自身 Model/首个 enabled 模型 → GetDefault 订阅，**总有可派生模型时必绑定**；③ `ResolveLLM` 的 `model == ""` 分支先 `ensureSessionModel` 修复绑定再重读（不再直接 fallback GetLLM 漂移）；④ `SetSessionLLM`/`setDefaultSubscription` 禁止写空 model（user_default_model → sub.Model → 首个 enabled 模型行，全空则报错拒写）。Tests: `agent/llm_factory_session_binding_test.go` 6 例（漂移复现：空 model 绑定的会话模型跟随 user_default_model 变化被 REPRODUCED；修复后绑定稳定 + 显示/压缩同源 + sender 残留兜底 + 空绑定修复 + balance-tier 之外的 fallback + SetSessionLLM 拒绝空 model）。
- **`thinking_mode` is a GLOBAL user setting, NOT subscription-scoped ("订阅是订阅，模型是模型").** Stored in `user_settings` under canonical channel `channel.ThinkingModeChannel == "cli"` (constant lives in the `channel` package to avoid the `channel/cli ↔ agent` import cycle). Surfaced via the main chat status-bar indicator (`🧠 auto|on|off [Ctrl+M]`, `renderReadyStatus` + `thinkingZoneXStart/End` click zone) and `Ctrl+M` toggle (`toggleThinkingMode` cycles `""→enabled→disabled→""`). `ResolveLLM` reads it via `f.userThinkingMode(senderID)` — priority per-model override (`pmc.thinkingMode`) → global user setting → `""`. `sub.ThinkingMode` is NO LONGER read (kept only as an internal fallback field). The `thinking_mode` `SettingHandlerRegistry` handler calls `f.InvalidateSender(senderID)` (no-op now — no in-memory cache to clear; DB is read fresh every turn). `cmd/xbot-cli/main.go` `ApplySettings` must NOT treat `thinking_mode` as an llm field (`updateActiveSubscription` no longer writes `sub.ThinkingMode`) — thinking flows only through `ApplyRuntimeSettings` → handler → `InvalidateSender`. Startup seeds the global user setting once (`serverapp`: `cfg.LLM.ThinkingMode` → default-sub `ThinkingMode` → `""`). Subscription add/edit/display panels are credentials-only (name/provider/base_url/api_key); `setLLMCmdForSub` shows only credential params.
- **`refreshRemoteValuesCache` MUST extract `max_context_tokens` from `PerModelConfigs[sub.Model].MaxContext`.** The function populates `valuesCache` which feeds `GetCurrentValues()` → `resolveMaxContext()` → context bar display. Without this extraction, the cache falls through to the `config.DefaultMaxContextTokens` (200000) fallback, causing the context bar to show wrong max context after settings save. The extraction must mirror the settings panel read path (`cli_settings.go:79-93`): PerModelConfigs[model].MaxContext → sub.MaxContext → config fallback. Also must NOT overwrite existing DB values from `GetSettings` (config tool wrote them via `SetSetting`).
- **`SwitchModel` with chatID must NOT call `SetModel` on the subscription.** Per-session model switches (with chatID) only create per-chat cache entries. Calling `SetModel` contaminates all sessions sharing the same subscription. Only user-level switches (no chatID) update the subscription.
- **`PerModelConfigs` is a read-side projection populated by the storage layer (v42).** `subscription_models` is the sole source for per-model config; the `per_model_configs` JSON column was dropped. `LLMSubscriptionService.List`/`Get`/`GetDefault` call `loadPerModelConfigs` (which reads `subscription_models`) AFTER closing the rows cursor — a nested query inside `rows.Next()` deadlocks the single-connection SQLite pool. `Add` upserts the incoming map into the table; `UpdatePerModelConfigs` does delete+reinsert. The old `mergeSubscriptionModels` in rpc_table was deleted (no longer needed). Client-side `ResolveEffectiveMaxContext`/`sub.PerModelConfigs` now see table values without an explicit merge step.
- **`IsDefault`/`Active` are read-side projections derived from `user_default_model` (v43).** The `is_default` column was dropped. `GetDefault` reads `user_default_model` → `Get(subID)` and marks `IsDefault=true`; `List`/`ListAll` mark via `markDefaultsFor`/`markDefaultsAll`. `SetDefault(id)` upserts `user_default_model`. `Add`/`Update` seed/sync `user_default_model` when `IsDefault=true`. `Get` does NOT populate `IsDefault` (stays false) — callers needing default-status use `GetDefault`/`List` or check `user_default_model` directly (e.g. `updateSubscription` RPC re-switches the user-level entry only if `GetUserDefaultModel` matches the edited sub).
- **System subscription REMOVED (v62); defaultLLM is the in-memory cfg.LLM fallback; models never travel alone (model-subscription integration).** The v44 system subscription (`id="system"`, `is_system=1`) was deleted — it was a bug farm (guard-matrix holes, list-order divergence, priority conflicts, `SetSystemLLM` ≡ `SetDefaults`, `defaultLLM` polluted by cli_user's personal subscription in multi-user deployments). Since v62: (1) `defaultLLM` is built ONCE from `cfg.LLM` (config.json + env) at `NewLLMFactory` time and is NEVER re-pointed (`SwitchSubscription` is a no-op hook; `SetSystemLLM`/`SetDefaults`/`SetConfigSubs`/`buildModelSubscriptionMap`/`configSubToLLMSubscription`/`ResolveSubIDForModel` are all deleted); it is a deployment-level fallback — not in DB, not in the picker, not selectable. (2) `GetDefault` returns `(nil, nil)` when the operator has no default — no system fallback. (3) `List`/`ListAll` no longer inject any shared row (the ByUserID variants were removed with the multi-user system in v63); `GetLLM` falls through to `defaultLLM`. (4) **Model-subscription integration invariant**: persisted/protocol-layer model references ALWAYS carry their owning subscription — tier values are strictly `"subID|model"` (`SetUserTierModel` rejects bare names), `get_default_model` RPC returns a `{sub_id, model}` object (`Client.GetDefaultModelPair`), `Agent.SetUserModel` requires subID, `iteration_history` carries `subscription_id` (v62 column; `GetTenantUsageStats` by_model groups by `(subscription_id, model)`), web `createSession` passes `subscription_id` alongside `model`, `GetLLMForModel` returns `(client, subID, model, ...)` as a pair (no `resolveSubIDForModel` second pass). Bare model names are allowed ONLY at human-input boundaries (SubAgent `model` param, tier names) and are resolved exactly once via `ResolveSubscriptionForModel` — the single input resolver. `GetLLMForModel` has NO "any subscription + arbitrary model name" hard-tries: a model without an owning subscription falls back to `defaultLLM` with a warning. The v62 migration deletes the system row + all references (user_default_model/tenants/subscription_models/user_identities), rewrites `system|model` tier values via owner re-resolution (unresolvable → cleared), and DROPs the `is_system` column (DB backed up to `*.pre-v62.bak` first via `VACUUM INTO`).
- **`handleSwitchLLMDoneMsg` must NOT pass `done.maxCtx` as `state.MaxContextTokens`.** Those values come from `resolveSubMaxContext` using the subscription's DEFAULT model. Setting them poisons `ResolveEffectiveMaxContext` priority-1 shortcut, bypassing per-model lookup. Let `applySessionLLMState` resolve dynamically from `PerModelConfigs`.

- **MCP stdio `exec.Command` uses process PATH, not `cmd.Env`.** Go's `exec.Command("npx", ...)` resolves the executable using the *process* PATH (`os.Getenv("PATH")`), ignoring `cmd.Env`. When xbot runs as a service with minimal PATH, tools like npx/nvm are invisible. `ConnectStdioServer` now calls `resolveCommand()` to pre-resolve the absolute path using the login shell PATH from `getLoginShellEnv()`. Also, `getLoginShellEnv` uses `bash -i -l` (interactive login shell) because `bash -l` alone skips `.bashrc` where nvm initializes.

- **MCP connections are POOLED, not per-session (tools/mcp_pool.go).** Every session used to own a full `SessionMCPManager` connection set — N sessions × M stdio servers = N×M child processes for identical config (config scope is global + per-sender, NEVER per-session). Now a process-level `MCPConnectionPool` keys entries by the scope 4-tuple (globalConfigPath, userConfigPath, workspaceRoot, userID); `SessionMCPManager` is a thin VIEW (public API unchanged). Three historical bugs fixed: (1) the 30-min inactivity timeout was a DEAD parameter (unload only ran for sessions evicted from the 24h session cache) — the pool reaper now reclaims entries with refCount==0 && idle > 30min every 30s, independent of session caches; (2) unloaded servers never reconnected (`initOnce` stayed 2) — a reaped entry is deleted; the next `Acquire` reconnects; (3) `UpdateScope` disconnected everything on a scope change — it now detaches from the old entry (kept alive for other sharers) and attaches to the new one. `InvalidateAllSessionMCP` wiring calls `GlobalMCPPool().InvalidateAll` directly (one call covers every scope). Tests: `tools/mcp_pool_test.go` (sharing/reaper/refcount/invalidate).

- **`SessionService.Replay` 必须用 `messageIndex` O(1) 查找，禁止对 `result.Messages` 线性扫描。** `GetHistoryBefore`/`GetHistory`（fetchHistory 切换会话时每次调用）全量 Replay。Replay 处理 mask/context_edit 记录时若用 `activeMessageIndexOccurrence`（O(N) 扫描）构成 **O(N²)**：tenant 119384 的 27442 条消息 + 1169 条 mask = 3200 万次扫描 → 秒级延迟 → 前端切换会话时历史过几秒才渲染（只剩 live iter）。修复：Replay 内维护 `messageIndex`（`map[int64][]int` HistoryID → 位置列表），消息追加 `msgIdx.add`、压缩重建 `newMessageIndex(result.Messages)`、查找 `msgIdx.occurrence(id, occ)`/`msgIdx.last(id)`。**禁止在 replayWith 里引入任何对 `result.Messages` 的全量扫描**（性能测试 `TestReplayMaskPerformance`：6000+6000 条 Replay 须 < 2s，实际 38ms）。
- **SQLite `datetime()` comparison with RFC3339 strings is a silent trap.** `created_at` stores `2026-05-24T14:00:00+08:00` (RFC3339 with timezone). `datetime(?, '-2 seconds')` returns `2026-05-24 05:59:58` (UTC, no timezone). Raw string comparison: `'T'` (0x54) > `' '` (0x20) at position 10, so `created_at > datetime(?)` is **always TRUE**, breaking any time-window dedup/filter. Always wrap both sides in `datetime()`: `datetime(created_at) > datetime(?, '-2 seconds')`.

### Append-Only History & Rewind (v52+)
- **`session_messages` is an append-only history log.** All content mutations (compress, context_edit, mask, AskUser Q&A) are appended as control records (`record_type` != `message`); current state is reconstructed by `SessionService.Replay()`. Physical DELETE only on rewind (`RewindToHistoryID`) and clear (`Clear`). `PurgeOldMessages` 已彻底删除（原 no-op 死链：agent/config/storage/session/serverapp 全链路移除）。
- **`ChatMessage.ID` (int64, `json:"-"`) is the stable DB auto-increment id** — used for rewind, trim, dedup, and append-only history node tracking. Never sent to the LLM. PR #256 originally named this `HistoryID`; it was unified to master's `ID` during the rebase. `HistoryMessage` (protocol) carries both `ID` (`json:"id"`) and `HistoryID` (`json:"history_id"`) — they are the same value, kept for client compatibility.
- **`appendMessageWith` MUST include `turn_id` in the INSERT.** The v50 migration added `turn_id` for turn-scoped dedup. `AddMessageWithID` delegates to `AppendMessage` (which calls `appendMessageWith`) — both acquire the striped `historyLock`. Never write to `session_messages` without holding `historyLock(tenantID)`.
- **Compound history writes use `withImmediateHistoryWrite` (`BEGIN IMMEDIATE`).** `AppendMessages`, `AppendMessagesAndAskQuestion`, `AppendControl`, `AppendContextSnapshot`, `RewindToHistoryID`, `ReplaceToolMessage` all use it. Do NOT use `conn.Begin()` (deferred tx) for history writes — it risks `SQLITE_BUSY` under the 4-connection pool.
- **`rewind` 必须按 `turn_id` 删除 `iteration_history`，不能只按 `message_id`。** `writeIterationHistory`（engine_run_tools.go）写入 iteration_history 时 `message_id=0`（读侧按 `turn_id` 查询，不关联具体消息）。旧版 `RewindToHistoryID` 只 `DELETE ... WHERE message_id IN (SELECT id FROM session_messages WHERE id >= ?)` —— `message_id=0` 永远匹配不到（session_messages.id 从 1 起），残留。server 重启后 `restoreTurnIDSeq` 从 DB 恢复 turn_id（复用被删的 turn_id）→ `GetIterationHistoryByTurn` 查到残留旧 iterations → 两个 turn 的 iterations 混在一起（用户报告："两个 agent turn 混一起，user1 消失"）。修复：删除条件改为 `turn_id IN (SELECT turn_id FROM session_messages WHERE id >= ? AND turn_id > 0) OR message_id IN (...)`。Test: `TestRewindDeletesIterationHistoryByTurnID`。
- **Session operation gate serializes Run + Rewind.** `chatProcessLoop` uses blocking `lock(ctx)`; `RewindHistory` uses non-blocking `tryLock()` (fails immediately if a Run is active). After DB truncation, in-memory caches (`lastProgressSnapshot`, `iterationHistories`, `streamState`, `PendingAskUser`) are cleared BEFORE the gate releases. The `history_rewound` session event is emitted while the gate is still held — it's a route-scoped transport barrier.
- **`broadcastHistoryResetLocked` unlocks `seqMu` internally** (mid-function, after `sequenceEventLocked`). The caller `broadcastSessionState` must NOT `defer seqMu.Unlock()` — it would double-unlock. The function acquires `seqMu.Lock()`, calls `broadcastHistoryResetLocked` (which unlocks), then returns.
- **Frontend `progressStore.lastIter` starts at `-1`** (not `0`). This ensures the first structured event (`iteration: 1`) does NOT clear stream-only fields (`streamContent`, `reasoningStreamContent`) — `hadPreviousIteration = lastIter >= 0` is false for the first iteration. Master used `0`; PR #256's `progressStore` requires `-1`.
- **Subscription-level enabled (v40) must be skipped in three places.** `user_llm_subscriptions.enabled=0` must be skipped by `ListAllModelsForUser` (both loops), `ResolveSubscriptionForModel` (`find` closure), and rejected by `SelectModel` — or disabling a subscription is cosmetic. `SetSubscriptionEnabled` must call `InvalidateSubscription(subID)`. `protocol.Subscription.Enabled` is a read-side projection from `user_llm_subscriptions.enabled` (via `subToChannel`/`LLMGetSubscription`); writes go through the `set_subscription_enabled` RPC.
- **No subscription switching in the UI; one unified LLM panel.** `cli_panel_quickswitch.go` is a SINGLE panel (opened by `Ctrl+N` / click status-bar model name / palette "Models & Subscriptions") that combines subscriptions + models + add actions in one flat `[]qsRow` list (`qsSection`/`qsSub`/`qsModel`/`qsAddSub`/`qsAddModel`). There is NO separate "subscription" panel and NO `Ctrl+P`/`Ctrl+N` anymore. Subscription rows are management-only (add/disable/delete); model rows switch cross-subscription. The old `SwitchLLM` async + `cliSwitchLLMDoneMsg` path is retained only for startup restore (`scheduleSessionLLMRestore`). Status bar shows `模型名(订阅名)` from `cachedSubName` (refreshed by `refreshCachedSubName` on `activeSubID` changes — NOT per-frame). `handleQuickSwitchKey` intercepts Esc/Up/Down/Enter over `quickSwitchRows` BEFORE other handling; in filter mode letters feed `quickSwitchFilterInput` and `rebuildLLMRows` re-filters. **Panel scrolling**: `quickSwitchScrollY` tracks vertical scroll offset; `ensureQuickSwitchCursorVisible` keeps cursor in view; `viewQuickSwitch` slices rows to `height - overhead` visible lines with a `── N-M / Total ──` scroll indicator. **Contextual hints**: `buildQuickSwitchHint()` renders row-type-specific operation hints (sub/model/add/section) in `PanelHint` style + common keys in `TextMutedSt`. **Model selection**: `✓` mark and `cursorToActiveLLMRow` match both `Model` AND `SubID == activeSubID` — same model name from different subscriptions is NOT a match. **Panel colors**: non-cursor rows use `TextSecondarySt` (not `TextMutedSt`); section headers use `PanelDivider`; disabled/offline models use `TextMutedSt`; cursor row uses `Accent`. **Thinking indicator**: `thinkingModeLabel()` returns ASCII `think`/`think+`/`think-` (no emoji, no `[Ctrl+M]` suffix); `think+` uses `Accent` style, `think-` uses `TextMutedSt`.

Owner attribution picks the best sub by status rank (normal>offline>disabled). The `CachedModels` snapshot is populated by the `OnModelsLoaded` callback — which the model-first refactor had **dropped** (must be re-wired via `makeOnModelsLoaded(subID)` in `createClientFromSub` + both entry-construction paths; the callback nil-checks `Get(subID)` before `UpdateCachedModels` since the latter nil-derefs on missing sub). ### Cron Scheduler
- **Cron 工具会话级隔离（tools/cron.go，与 web 面板同一边界）。** `listJobs` 用 `ListJobsByChannelChatID(channel, chatID)`（不再 `ListJobsBySender`——sender 维度会跨会话泄漏），`removeJob` 验证 `job.Channel+ChatID` 与调用会话匹配（不再 SenderID——subagent 创建的 job 归属主会话，主会话内可删）。subagent 的 `ctx.ChatID` = root origin（`buildSubAgentRunConfig` 从 parentCtx 继承）→ **subagent 创建的 cron job 天然归属主会话**（主会话可见可删，其他会话不可见——TestCronToolSubAgentJobsBelongToParentSession）。跨会话 remove 返回 "not found"（不泄漏存在性），与 web 面板 CronTasks callback（`ListJobsByChannelChatID`）边界一致。subagent 的 BgSessionKey 保持 subAgentID 隔离设计不变（bg task 通知不污染主会话，subagent 用 task_wait 轮询）。Tests: `tools/cron_session_test.go`（跨会话不可见/不可删 + subagent 归属主会话）。
- **`cleanupExpiredJobs` must NOT delete `delay_seconds` one-shot jobs.** `delay_seconds` represents relative time ("N seconds from creation"). If the job expired during downtime, deleting it silently drops the user's scheduled reminder. Keep expired `delay_seconds` jobs so `checkAndFire` triggers them on the first tick. Only `at`-based one-shot jobs (absolute time point) should be removed when expired — the scheduled moment has passed.
- **`every_seconds` next_run must be based on `job.NextRun`, NOT `now`.** The old code used `nextRun = now.Add(interval)`, where `now` is the actual fire time (delayed by 0–5s due to the 5s ticker). Each fire accumulates drift, causing the schedule to slide later and later. Fix: `nextRun = job.NextRun.Add(interval)` anchored to the planned schedule, with a forward-advance loop for missed intervals.
- **Recurring jobs skip missed executions on restart (by design).** `cleanupExpiredJobs` recalculates `next_run` from `now` for recurring jobs. This matches traditional cron semantics — no catch-up execution.

### Startup
- **⛔ 停机必须先把 WAL 的已提交内容 checkpoint 进主库（2026-09-17 丢数据事故；`sqlite.(*DB).CheckpointForShutdown`）**：`[program:xbot-server]` 未配 `stopwaitsecs`（默认 10s），而停机在某些状态（插件 deactivate / 进度推送 broken pipe / agent loop 未及时退出）会挂住 ⇒ 被 SIGKILL；那一刻"已 ack 但只在 WAL 里"的写入永久丢失。实测：约 2 分钟的 turn 迭代（日志口径跑到 12:47:41 / `msg_count=2938`）与 2 条 `pending_resumes`（12:47:33 写入、日志显示成功）**同时在库里消失**，DB 最后写入停在 12:45:47，连 15 秒后的全量 `VACUUM INTO` 快照里也没有它们 ⇒ 那段 WAL 没被接手进程应用（具体 actor 未证明；当时无任何 DB 错误日志）。**契约**：`serverapp` 停机序列必须是 `collectPendingResumes`（恢复标记先落库）→ `cancel()` → **`webDB.CheckpointForShutdown()`**（`PRAGMA wal_checkpoint(TRUNCATE)`：全帧写主库 + 重置 WAL；受 `busy_timeout(10s)` 约束、重试一次、失败只 WARN、绝不阻塞停机）→ 之后才是 webhook / dispatcher / 插件收尾（**这几步才是会卡住的那部分，checkpoint 必须排在它们之前**）。配套 `stopwaitsecs=120`（`supervisord.conf`；改后 `reread`，**别随手 `update`——它会重启 server**）。**埋点（零风险、纯日志）**：`sqlite.Open/Close` 记调用方 `file:line`；`logWALState` 记 WAL 存在性/size，并把"曾被观测到 → 路径消失"判为 `missing`（**不依赖 inode** —— overlayfs 会复用 inode，`os.SameFile` 不可靠）。**判据教训**：**DB 里 `iteration_history` 无缺号 ≠ 没丢**（那只是"库里到哪儿为止"），必须用日志（`-t<turn>-<iter>` / `msg_count` / `Tool done`）对账"进程跑到哪儿"。另：schema 变更启动时同步 `VACUUM INTO` 2.8GB 备份 ≈18s 只是**风险放大器**（启动窗口变长），**不是**本次丢数的原因（丢失窗口比它早 2 分钟）。Tests: `storage/sqlite/db_shutdown_checkpoint_test.go`（checkpoint 前"主库文件单独读"0 行 → 之后 2 行；变异自证：把 checkpoint 改 no-op ⇒ 测试红）。

- PowerShell env output is newline-delimited, not null-delimited.
- **Windows CI hook command tests need generous timeouts (`agent/hooks/executor_command_test.go` `testTimeout=60s`).** powershell.exe has a 5-10s cold-start (.NET CLR) on CI runners, and a loaded runner can push an echo round-trip past 30s — `TestCommandExecutor_Success` timed out at 30.57s on a Test (Windows) job while the identical code passed on the next run (flaky). Tests that assert successful execution must NOT use tight timeouts; tests that deliberately exercise the timeout path use their own short values.
