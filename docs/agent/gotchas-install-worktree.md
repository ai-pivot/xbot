### Installation & Release (One-Click Setup)
- **⚠️ `setup` 能力探针必须只有一处实现，且绝不能用管道喂 grep（2026-09-11 事故：装 stable 静默变成 nightly）。** 探针逻辑（`${BINARY} setup -h` 打印 `Usage: xbot-cli setup` ⇒ 该二进制支持 setup）曾在 `main()` 的 nightly 重试与 `run_setup()` 里**各写一份**，只修了一份 → 另一份仍是 `! "${BINARY}" setup -h 2>/dev/null | grep -q "Usage: xbot-cli setup"`。脚本跑在 `set -o pipefail` 下，管道取最右非零退出码，而 `setup -h` 在某些路径非零退出 → **探针对任何二进制都判"不支持"** → 默认 stable 渠道的新装机必然被重试逻辑换成 nightly（用户选正式版却拿到 nightly 构建）。修复：单一 `binary_has_setup()` helper（here-string + `|| true`），两个调用点共用；**新增能力探针一律走它**。教训：① 同一判定写两遍必然漂移——抽函数；② `set -o pipefail` 下 `cmd | grep -q` 的退出码来自整条管道，`cmd` 可能非零（help flag 惯例）→ 用 `<<<` here-string 或 `cmd >/dev/null 2>&1 || true` 先取值再判。**CI 的 install-test 覆盖不到这条**：full-setup job 用 `INSTALL_LOCAL_BINARY=1`/`CHANNEL=nightly` 跳过重试分支，其他 job 用 `VERSION=v0.0.23`（本就该重试）——所以**发布后必须真机跑一次默认 stable 安装**，只信 CI 绿色会漏。
- **`xbot-cli setup` 子命令（cmd/xbot-cli/setup.go）是安装补齐的唯一权威**：下载 web dist（`xbot-web-dist.tar.gz`）+ 内置插件 tarball（`xbot-plugins-{os}-{arch}.tar.gz`，版本对齐二进制的 release tag）→ 装到 `$XBOT_HOME/web/dist` + `$XBOT_HOME/plugins/builtin/` + channels 激活配置。install.sh/install.ps1 只装二进制 + 写 config，**web/plugins/channels 全部委托 setup**（bash/PowerShell 双份逻辑已消除）。flags：`--check`（诊断 exit 1）、`--config-only`、`--offline-web/--offline-plugins <file>`（air-gapped）、`--tag`、`--mirror`、`--force`。tag 推导（`deriveReleaseTag`）：`--tag` > env `XBOT_RELEASE_TAG` > channel=nightly → 固定 tag `"nightly"`（nightly 是覆盖式发布，binary Version 是 nightly-DATE-SHA **不等于** tag）/ stable|beta → Version 即 tag；dev build 拒绝下载（报错指引 --offline/--tag）。
- **发正式版流程（stable）**：版本号不硬编码在仓库里，**完全由 tag 驱动**——`git tag -a vX.Y.Z <master sha>` → `git push origin vX.Y.Z` → `release.yml` 触发（`on.push.tags: 'v*'`）→ `softprops/action-gh-release` 建 release（`prerelease=false`）。tag 不带 `-` 就是 stable，带 `-`（如 `-beta.1`）自动判 beta。**当前 stable 资产应为 12 个**：5 个二进制 + `xbot-web-dist.tar.gz` + 5 个 `xbot-plugins-*.tar.gz` + `checksums.txt`（早期 release 只有 7 个，没有 web/插件包）。CHANGELOG.md 自 v0.0.40 后**未随发布维护**（不必手工补）；发布前确认 `gh pr list` 无遗留 PR + master 的 CI/Install Script Tests/Release/Deploy Docs 全绿。
- **下载 404（老 release 无插件 tarball）→ `errSetupIncomplete` exit 3（软失败）**：install.sh/ps1 捕获后 warn 不中断（旧 release 仍可装二进制+web dist）；checksums.txt 缺失 → warn 跳过校验（镜像 install.sh 语义）；checksum mismatch → 硬错误。仓库 fallback：ai-pivot/xbot → CjiW/xbot。GH_MIRROR 协议 `https://{mirror}/https://github.com/...`（api.github.com 不代理）。
- **版本戳是 sidecar 文件，不放被扫描/服务目录**：`$XBOT_HOME/web/.dist-version` + `$XBOT_HOME/plugins/.builtin-version`（**不是** web/dist 或 plugins/builtin 里面——避免污染静态服务目录 + 插件发现）。stamp 内容 = **安装时二进制的 version.Version**（不是 tag——nightly tag 固定 "nightly" 用 tag 做 stamp 会永远跳过更新；version 每次构建变 → 升级自动重下）。跳过条件：stamp == 当前二进制 version 且 `componentInstalled`（web→dist/index.html；plugins→builtin 下任一插件目录有 plugin.json——**plugin.json 在 builtin 的子目录里，不在根上**）。
- **插件装 `plugins/builtin/`，不装 `plugins/`**：`DefaultPluginDirs` 顺序 plugins → plugins/builtin → XBOT_PLUGIN_DIRS，first-match-wins dedup → **用户目录副本天然覆盖 builtin**（override 语义免费）。`make plugins-install`（dev 语义）仍装用户目录——本地构建永远优先于 release 分发版本。Discovery 跳过非目录条目（manifest.go `if !entry.IsDir() { continue }`），tarball 根的 `.xbot-version` stamp 文件在 builtin/ 里无害。
- **channels 激活修复是 manifest 驱动 + set_if_missing + builtin-only 边界**：`fixChannelActivationConfig`（setup.go）**只扫 `plugins/builtin/`**（setup 自己装的 release 插件）的 plugin.json `contributes.channelProvider.config_schema[].{key:"enabled", default_value:"true"}` → 只在 config.json 的 `channels.<name>.enabled` **不存在时**写 `"true"`（用户显式 false 永不覆盖——"装了不生效"根因修复）。**用户目录 `plugins/` 的插件绝不激活、绝不报缺失**（setup 只管理 builtin——用户目录的示例/实验/自装插件是用户自己的决定；2026-09-08 事故教训：`--check` 曾把用户目录的 `com.example.echo-channel` 报成 "Channel: echo MISSING"，用户以为 setup 装了它——`scanChannelActivation` 由此收窄为 builtin-only）。`--check` 的 Plugins 检查分两层：builtin（完整性判断基准，MISSING = 可跑 setup 修复）+ user-dir（info 行 "user-managed, not judged by setup"——dev 机器 git-fancy 在用户目录装着时不再误报 MISSING）；Channel 行只报 builtin 插件。配置写入走 `config.LoadFromFile` → 修改 → `SaveToFile`（deep merge 保留未知字段）。`--check` 另有**本机体检**（`pluginHealthFindings` ← `scanLocalPluginHealth` 打印，report-only、**不改退出码**）：扫描 user + builtin 两层全部插件的 plugin.json —— manifest 可读/校验 + 声明 `web.entry` 的产物存在性 + **stdio/grpc 插件的入口二进制**（存在且可执行；windows 上按 `plugin/runtime.go` 同一规则允许 `.exe` sibling；entry 是绝对路径/带参数命令行/script runtime 时跳过，不造假警），missing 与 disabled（`plugins.disabled_plugins`）分组逐行列出；退出码仍只由 pinned 缺失决定（本地装过又删的插件不能被误判成"安装失败"，2026-09-16 iter-stats 产物丢失属此类、只报告不报警）。⚠️ **「绝对路径」的判定必须 GOOS 无关**：`filepath.IsAbs("/usr/bin/node")` 在 **windows 上是 false**（windows 要求盘符）⇒ 异平台写法会被当成"随包相对二进制"、报出假的 `plugin binary missing`（CI `Test (Windows)` 实测）。判据 = `filepath.IsAbs` **或** 前导 `/`、`\` **或** windows 盘符形式 `C:\`/`C:/`；`TestShippedBinaryPath_Predicate` 覆盖四种形态（跨平台确定性，本机即可验证）。入口二进制这一条是 2026-09-20 补的：web 产物缺失有守卫、**二进制缺失此前没有任何检查**（插件进程起不来、运行期静默），install-test 里也只有 genui/git-fancy 两个硬编码名字被断言 —— 现在 install-test 的枚举循环同时断言 `web.entry` 产物与 entry 二进制（manifest 驱动，新插件自动覆盖）。
- **release.yml 产物矩阵**：frontend job 追加 esbuild 插件 web 资产 —— **每个声明 `web.entry` 的插件都要构建**，esbuild 产物按插件目录形状落盘 `build/plugin-web/<plugin-id>/web/`（`--splitting` 让该插件的 view 入口共享同一份 rpc/ui 单例 chunk；**每个插件单独一次 esbuild 调用**，不要跨插件共用一个 outdir）→ artifact `plugin-web-dist`；`build-plugins` job（单 ubuntu runner，CGO_ENABLED=0 交叉编译 5 平台）调 `plugins/package.sh --out dist --web-dist-dir build/plugin-web` → 5 个 `xbot-plugins-{os}-{arch}.tar.gz` 进 release + checksums.txt。⚠️ **历史事故（2026-09-11）**：只构建了 git-fancy，genui（`web/src/plugins/genui/index.tsx` —— display_html / `uiMode=genui` 渲染器，经 `/plugins/xbot.genui/web/index.js` 动态加载）**从未构建** → release 安装里 genui UI 渲染器从来没被加载过。新增插件 web 入口时必须同步加一次 esbuild。⚠️ **历史事故（2026-09-16，同盲区复发）**：`xbot.iteration-stats`（源码 `web/src/plugins/iteration-stats/entry.tsx`；单入口、模块不 import 任何东西 → 构建用 `--outfile=.../web/index.js` 直出固定名，不需要 `--splitting`）既不在 frontend job 的两个硬编码块里、`plugins/xbot-iteration-stats/plugin.json` 也从未入库 → 从未进 `build/plugin-web/` → `package.sh` 收不到 → **从未进发布包**，且本机删掉后任何检查/CI 都看不见（install-test 彼时只硬断言 genui/git-fancy 两个名字；404 静默）。修复：manifest 入库 + 新增 iteration-stats 构建块 + 步骤末尾**枚举守卫**（`for pj in ../plugins/*/plugin.json`，jq 取 `id`/`web.entry`，凡声明 `web.entry` 而无 `build/plugin-web/<id>/web/<entry>` 产物 → exit 1，防再加新插件时重蹈覆辙；id→源码 entry 无法可靠推导——输出名是 `web.entry` 而源文件可叫任意 `*.tsx`——故构建块保持显式)。
- **plugins/package.sh 通用打包**：遍历 `plugins/*/plugin.json`（**源目录用连字符 `xbot-genui`，插件 ID 用点 `xbot.genui`——tarball 内是 ID 布局，脚本维护 src-dir→ID 映射**）；runtime stdio/grpc → `go build` 交叉编译 entry 二进制（**windows 平台加 `.exe` 后缀**，plugin.json entry 平台无关）；runtime script → 纯拷贝 plugin.json；web 资产两条来源都落到 `<plugin>/web/`：源目录 `web/` **内容**（`cp -R "$plugin_dir/web/." "$dest/web/"`）+ `--web-dist-dir/<id>/web/` **内容**（esbuild 产物，⚠️ **dist 目录是插件目录形状，web 文件在 `<id>/web/` 下** —— 曾错误地拷 `$WEB_DIST_DIR/$id/.` 导致 `<plugin>/web/web/index.js` 多嵌套一层，web 层 `/plugins/<id>/web/<web.entry>` 404，nightly 连续发坏包）；**打包末尾守卫**：插件声明了 `web.entry` 却打不出 `<plugin>/web/<entry>` 时**直接 build 失败**（把问题提前到打包阶段而不是等 install-test 发现）；tarball 根写 `.xbot-version`。JSON 解析 jq 优先 python3 fallback（CI 有 jq，dev 机不一定），`json_get` 支持点号路径（`web.entry`）。
- **PR CI 覆盖插件模块（独立 `plugins/*/go.mod`）**：根模块的 `go build ./...`/`go test ./...` **永远到不了它们**（嵌套 module 被 Go 排除），所以此前**插件编译失败或自身测试失败只在 release 的 build-plugins job 才暴露**（= 发布时）。`ci.yml` 的 `test` job 新增一步：遍历 `plugins/*/`，有 `go.mod` 就 `go build ./...` + 交叉编译 release 目标（`windows/amd64`、`linux/arm64`、`darwin/arm64`，CGO_ENABLED=0）+ `go test -race ./...`。⚠️ **必须跳过「非测试源码为零」的模块**（`xbot.iteration-stats` 只有 `manifest_i18n_test.go` + plugin.json）：那里 `go build ./...` 打印 `no packages to build` 并 **exit 1**（`go test` 正常）——用「有非 `*_test.go` 源码才 build」的判据。新增内置插件（如 `xbot.ssh-runner`）自动被 glob 覆盖，不需要改名单。
- **`resolvePluginBinary`（plugin/runtime.go）在 windows 上为无后缀 entry 解析 `.exe` sibling**：release tarball 的 windows 二进制是 `bin/genui-plugin.exe` 而 plugin.json entry 是平台无关的 `./bin/genui-plugin`——`startPluginProcess` 对无 `.exe` 后缀的相对路径在插件目录 stat `<entry>.exe`，存在则用后缀名。纯函数 + goos 参数注入（`runtime_entry_test.go` 全平台可测）。
- **Makefile**：`make setup` = web-build + **plugins-install-builtin**（装 `$(XBOT_HOME)/plugins/builtin/`——与 setup 的管理边界一致，`--config-only` 只扫 builtin 激活 channels）+ 拷 dist 到 `$(XBOT_HOME)/web/dist` + `./xbot-cli setup --config-only`（源码用户一条命令）；`make plugins-install`（dev 语义）装**用户目录** `plugins/`（first-match-wins 覆盖 builtin——本地构建永远优先于 release 分发版本）；`plugins-install-builtin`（PLUGIN_DIR override 装 builtin）是 setup 的安装目标；`plugins-web`（esbuild git-fancy 资产 → `plugins/xbot-git-fancy/web/`，源内产物 gitignore `plugins/*/web/`）；`plugins-package`（本地 release 式打包）；`plugins-install` 补齐 git-fancy web 资产 + xbot.ambience（script runtime，manifest-only）——此前 ambience 和 web 资产都不装。

### Worktree
- **`RegisterPeer` always uses role="peer" — no primary concept.** Every session is an equal peer for awareness purposes. `WorktreeTool.init` and `AutoDetectAndInit` both create physical worktrees for each session. Only worktree creation requires `git worktree add` which uses `--detach HEAD` (works on dirty trees too).
- **`createWorktree` uses `--detach` not `-b`.** `git worktree add --detach HEAD` followed by `checkout -b` in the worktree. This avoids dirty-tree failures that `-b` would trigger.
- **AutoDetectAndInit runs in `buildPrompt` (not `processMessage`).** `buildPrompt` is the common code path for ALL message types. Session CWD is updated before system prompt construction.
- **`IsWorktreeIsolated` overrides `isUnrestricted()`.** CLI mode (`sandbox="none"`) normally bypasses all path checks, but when `IsWorktreeIsolated=true`, `isUnrestricted()` returns `false`.
- **Worktree paths must be outside main repo.** Git rejects `git worktree add` inside the main working tree. Paths: `{repo}/../.xbot-worktrees/{role}-{instance}/`.
- **Worktree creation is serialized via `GlobalWorktreeRegistry.mu`.** Two agents creating worktrees simultaneously would race on `.git/worktrees/` lockfiles.
- **Registry persisted per-repo to `{repo}/../.xbot-worktrees/registry.json`.** `saveRepoLocked` uses atomic tmp+rename. `ensureLoaded` lazily restores on first access. Orphaned worktree directories are skipped on load.
- **`BuildSystemReminder` takes `sessionKey` parameter.** Used to query `GlobalWorktreeRegistry` for worktree/peer info injected into sys_reminder per iteration.
- **`MethodSetCWD` only sets CWD when empty.** Prevents CLI session switch from overwriting worktree CWD with main workspace path. Session-specific CWDs (worktree, Cd tool) are preserved.
- **`go:embed embed_skills/*` auto-discovers new skills.** Adding a directory under `tools/embed_skills/` requires zero code changes.
- **`buildPrompt` 绝不恢复 CWD 到 worktree 路径。** 当 session 已注册后 `AutoDetectAndInit` 跳过，这是正确行为。agent 通过 Cd 工具主动切换的目录必须被尊重，如果在后续 buildPrompt 中强制恢复会破坏 agent 的 Cd 操作，产生人机对抗。
- **Cd 工具绝不强制 worktree 边界。** CLI 模式下 Cd 允许 agent 自由导航到任何目录，包括主仓库。如果对 Cd 加边界限制会导致 agent 无法读取 worktree 外的文件（如 AGENTS.md、知识库、配置文件），这是严重 bug。worktree 隔离是软性的工作指引，不是硬性监狱。
- **新会话绝不能进入老 worktree（纵深防御 6 层）。** `loadPersistedCWD` 拒绝加载 worktree 路径和不存在目录 → `autoDetectAndInitInto` 拒绝从 worktree CWD 创建 worktree + 自动清理 worktreeDir 不存在的孤儿条目 → `buildPrompt` 验证 worktree 所有权（不匹配则重置到 workspaceRoot）→ `showSessionCreateDialog` 和 `/chat new` 新建前清理 worktree registry + persisted CWD + savedSessions + todos。详见 `docs/agent/worktree.md`。
- **`progressStore.replace()` 绝不能抬高 `eventSeq`（hydration/切换恢复）**——eventSeq 是 SSE `progress.seq` 水印，只能由**实时 SSE 事件**驱动。`active_progress.eventSeq` 是服务器端**全局** progress 计数器（数千级），而后续 SSE 事件带**小数字**的 per-stream `progress.seq`（如 47）。replace 取 max 会把 store.eventSeq 抬到服务器水印 → **后续所有 SSE 事件 `progress.seq <= eventSeq` 被判 stale 丢弃 → store 冻结 → turn 消失**（用户报告："切换会话后 turn 消失，rowsLen=0"；`GetActiveProgress` 恢复 snapshot 后 store 停止更新）。✅ **已修复（V1，2026-08）**：`replace()` 移除 eventSeq max 逻辑，与 `resetAndReplace()`（注释 "MUST NOT"）对齐——replace 只恢复数据（iterationHistory union、completedTools 过滤、lastIter 重算），eventSeq 从 `rest` 解构中排除（`void _es`），绝不参与 stale 水印。两个函数现在语义一致，不再互相矛盾。Test: `progressStore.test.ts` "replace() 不得抬高 eventSeq（V1 — hydration 水印污染）"。
- **`MessageStore.bindUser` 必须优先按 `TurnStartInfo.RequestID` 精确匹配（V2）**——`bindUser` 原本从后往前绑定"最后一条 `!persisted` 的 pending user"。两条消息快速连发 + REST 响应慢时，`turn_started(msg1)` 会误绑 msg2 到 turn1 的 slot（弱网下短暂顺序错乱，R2 违反；靠 user_echo/REST 最终纠正）。后端 `TurnStartInfo.RequestID`（protocol/events.go:155，JSON tag `request_id`）已存在却未使用。✅ **已修复**：`bindUser(turnID, requestID?)` 先按 requestID 精确匹配 pending（无则 fallback 最后一条）；`useProgressStream` turn_started 分支 `beginTurn(p.turn_id, { resume, requestID: ts?.request_id })` 传入。**注意 JSON tag 是 snake_case `request_id`，前端必须读 `ts?.request_id` 不是 `ts?.requestID`**（camelCase 是 undefined → 修复失效）。Test: `messageStore.test.ts` "beginTurn 带 requestID → 精确绑定对应乐观 user"。
- **`historyReady` gate 期间丢弃的 SSE live 必须在 ready 后补写（V3）**——gate（`writeLiveToMessageStore` 开头 `if (!historyReady) return`）丢弃的是 MessageStore 写入；ProgressStore 一直累积。若 turn 在 fetch 后、`historyReady=true` 前开始且 `active_progress=null`（hydration 无兜底），gate 期间到达的早期迭代是**增量 delta**——丢弃后无其他来源可补（`onIterationGap` 只查内部 gap，不覆盖"从未收到"）。✅ **已修复**：`useProgressStream` 新增 V3 effect——`historyReady` false→true 时，若 `store.lastTurnID > 0` 且 `hasVisibleProgress(store)` 且 `!messageStore.hasLive(lastTurnID)`，用 ProgressStore 当前快照补写 MessageStore（等效 hydration）。**仅当 MessageStore 无该 turn 的 live 时补写**（有 live = 后续 SSE 已接管，快照可能滞后不能覆盖）。Test: `useProgressStream.test.ts` "V3: historyReady gate 期间丢弃的早期迭代在 ready 后补写（缓冲回放）"。
