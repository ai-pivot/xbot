## 2026-09-17 追加（本轮三条 gotcha）

- **⛔ 注入型（fake）工具【绝不】在 content 里声明「这不是你调用的工具」（2026-09-17 用户纠正，取代同日早些时候的做法）**：`agent.syntheticInjectionNotice()` 已**整体删除**，`newSyntheticToolPair` 不再给注入工具的结果加任何前缀 —— 注入结果就是一段普通 tool-result 文本（与 Shell/Read 输出同形态）。原因（实证）：旧前缀写「不是你调用的工具、你从未调用过它、不要回谢、不要试图再次调用它」后，模型会在思考里写出「**我注意到自己在反复误触一个不存在的工具**」（subagent 截图 + 本会话现场注入双重证据）—— **反向暗示凭空造出一个"不存在的工具"的焦虑，比不加提示更糟**。用户原话：「我们自己注入的不要告诉他别调用，否则他会以为这个是他自己调用的」。**真正由模型主动调用**的工具（task_status / task_read / SubAgent inspect）仍带 `tools.PollingHint`（那才是需要劝导的场景，见 `TestTaskFormats_CarryPollingHint`）。守护：`agent/synthetic_tool_pair_test.go`（content 必须与传入 verbatim 相等 + 六个禁用串零命中）。
- **`<system-reminder>` 注入块的跳过模式【只能】由 `</system-reminder>` 结束，空行不结束（2026-09-17 实证 bug：memory 整块被当"用户消息"回显进每轮 reminder）**：`extractUserGoal`（agent/reminder.go）原先用 `inGuide` 跟踪该块，而 `inGuide` 会被**空行**解除 —— memory 的 CDATA 正文**恰好以空行开头**（`MemoryMiddleware` 注入 `# Memory\n\n## Core…`）⇒ 包装行被吞、`## Core` 整块 memory 被塞进**每一轮**的 `<user-msg>`（实测 reminder 818→603 字符、`hasCore` true→false；生产 memory 正文 ≤2000 字符且每迭代重复，并让模型把 memory 误读成用户输入）。修复：新增独立状态 `inReminder`（只由 `</system-reminder>` 置回 false，空行无效），块内所有行一律跳过。守护：`TestBuildSystemReminder_MemoryBlockDoesNotLeakIntoUserMsg`（旧代码下必红）。
- **reminder 的 `<note>` 从简**：删掉 "It is NOT a user message or tool result — do not acknowledge, reply to, or confirm it" 长句，仅保留一句 `Auto-injected system reminder for this iteration (not a user message). <user-msg> = the original user message, for context.`（用户 2026-09-17：「note 也可以简化一下」—— 过度解释本身会被误读）。守护：`TestBuildSystemReminder_Basic` 断言不得出现 `do not acknowledge`。
- **飞书 CoT 不再输出 reasoning（可一键恢复）**：唯一写出点 `feishuCoTRenderer.emitReasoningLocked` 用 `cotEmitReasoning = false` 掐断（两条来源同时生效；`flushReasoningLocked`/`closeReasoningLocked` 自然退化为 no-op）。用户 2026-09-17：「cot 模式不渲染 reasoning 了，只渲染 content。reasoning 太多了」。契约变更后**旧契约测试要删**（5 个断言 reasoning 存在的用例），保留 `TestFeishuCoTRenderer_NoReasoningEvents` 守护「绝不出现 REASONING_MESSAGE_*」。置 true 即恢复（渲染逻辑完整保留）。
- **⛔ 飞书原生 CoT 的「停止生成」按钮必须处理（2026-09-23 用户报告「中止按钮没处理」）**：平台契约 —— 用户点 CoT 消息上的「停止生成」时，飞书发 `card.action.trigger` 回调，**`action.tag == "cot_stop"`**（value 带 cot_id/message_id；dsh-lark 也没处理这个，是 xbot 自己补的）。此前该回调落到通用卡片路径被当 unknown tag **静默丢弃** —— 按钮完全无效。处理链路（`channel/feishu`）：① `onCardAction` **最先**拦截 `handleCoTStopAction`（在 approval/askuser 之前 —— cot_stop 不是 button/form_submit，晚拦会被 generic 路径吃掉）；② 匹配渲染器：优先 `value.cot_id` 精确匹配（渲染器已创建时），渲染器未创建（还没写过事件、cot_id 空）或 cot_id 缺失时按回调 `open_chat_id`（与 `cot.chatID` 同源的真实会话 id）匹配；③ 停止 = `renderer.stop()`（emit RUN_ERROR「用户停止了生成」+ `cot.stop()` 标记 stopped —— **后续 emit 全部丢弃**，平台侧不"复活"）+ 发 `/cancel` 到 msgBus（与 AskUser cancel 同模式，按 channel:chatID 路由到正在跑的 turn）；④ 无活跃渲染器时按钮仍被消费（toast「没有正在进行的生成」，不 panic 不发 cancel）。守护：`feishu_cot_stop_test.go`（RUN_ERROR + 停止后事件丢弃 / 匹配 + /cancel / 无活跃 run / 非 cot_stop 不拦截 / cot_id 精确匹配不误伤其他会话）。
- **⛔ 飞书 CoT 测试必须禁用异步 drainer（走 `newFakeCoT`），否则 flaky（2026-09-23 master CI 失败根治）**：`feishuCoT.emit` 会 `go c.drain()` 启动异步写线程；测试若**直接** `newFeishuCoT(...)`（不设 `c.draining = true`）再调 `flushNow()`，两个写线程会争抢同一 `pending` 队列 —— drain 先取批时把 create 失败消费掉（重试 3 次后置 `broken` + `pending=nil`），`flushNow` 只看到空队列/已 broken 便**返回 nil** ⇒ 断言非确定（Windows 调度下必现：CI 实测 `expected create rejection`；Linux 通常 flushNow 抢到；**`-race` 抓不到** —— 这不是数据竞争，是"谁先取批"的时序竞态）。**契约：所有直接构造 `feishuCoT` 的测试一律走 `newFakeCoT`（它设 `draining=true` ⇒ 唯一写线程 = flushNow ⇒ 断言确定）**；需要自定义失败 request 时用 `c, _ := newFakeCoT(...)` 再覆盖 `c.request`。**历史教训（同类 flaky 修了两次）**：`TestFeishuCoT_CreateFailureMarksBroken` 首次出现时只"改断言容忍两种时序"（治标——`flushErr == nil && !brokenNow()`），而 `TestFeishuCoT_CreateRejectedSurfacesPlatformMsg` 漏改、仍硬性要求 `err != nil` ⇒ 同一 flaky 复发并打挂 master CI；本轮两处统一**禁用 drainer**（根因修复）+ 恢复精确断言。判别力证据（可复现）：旧写法下主动让 drain 先跑（轮询 `brokenNow()`）⇒ `broken=true` 但 `flushNow` 返回 nil —— 正是 CI 失败机制。
- **MCP 服务器管理 = 工具面板的 server 分组**：`tools.MCPServerName(tool)`（真实 server 名，来自 MCP bridge 的 `mcpSchemaProvider.mcpServerName()`，**不要用工具名前缀猜**）→ `Agent.ToolSetting.ServerName` → 前端 `SettingsTools` 按 server 分组 + 服务器级主开关（批量 `set_tool_enabled`，无新增后端语义，激活集过滤即"未激活不进上下文且不可执行"）。注意 `ToolSettings()` 里局部变量**不要命名 `tools`**（会遮蔽 `tools` 包 → `tools.MCPServerName undefined`，本轮踩过）。

- **interactive SubAgent 寻址必须经唯一解析器（2026-09-17「全收口」）**：所有按 `(role, instance)` 寻址的入口（`SendToInteractiveSession` / `InspectInteractiveSession` / `InterruptInteractiveSession` / `UnloadInteractiveSession` / `ContinueInteractiveSession`）**只能**走 `Agent.resolveInteractiveSessionKey`，禁止各自写 `interactiveKey(...)+Load`。契约：①精确地址键命中即用；②否则在自己的 subagent 列表里 **best-effort 匹配**（`matchInteractiveSessions`：role/instance 任一为空即该维度通配）——现场故障就是 `{"action":"send","instance":"perf-slot"}` **漏传 role**，旧实现用调用方上下文精确查 ⇒ 必然 miss ⇒ 报出误导性的 `no active interactive session for role "" ... use interactive=true`（会话其实活着）；③**唯一命中**即用；**0 个**→报错并列出 `available`；**多个**→报歧义并列出 `candidates`（绝不静默送到错的会话，也绝不因漏一个字段就误报"没建过"）。测试：`agent/interactive_match_test.go`。**⚠️ best-effort 的作用域 = 发起者的整棵子树（2026-09-18 用户报告）**：曾限定 `pk == parentKey`（只认**直接子级**）—— 孙级（主 agent → `explore:mma3` → `explore:mma4-tcgen05`）的 `SubAgent(action="send", instance="mma4-tcgen05")` 因此 0 命中，报 `no sub-agent with instance="mma4-tcgen05" in your sub-agent tree (role=""; your tree: [web:chat_A/explore:mma3] …)`（补上 `role` 走精确地址键就通 —— **两条路径作用域不一致**正是本 bug）。修复：新增 `isDescendantSessionKey(child, ancestor)`（`ancestor != "" && child != ancestor && strings.HasPrefix(child, ancestor+"/")`），匹配条件放宽为「本树 **或** 子树内」——**跨树仍然严格排除**（绝不自动 fallback 到别的会话）。测试：`TestResolveInteractiveSessionKey_GrandchildInstanceMatch`（仅 instance 命中孙级 / 带 role 命中 / `chat_B` 跨树不命中 / 本树列表含孙级）+ 既有 `TestMatchInteractiveSessionsBestEffort` / `TestResolveInteractiveSessionKey_TreeScopedInstanceMatch` / `TestResolveInteractiveSessionKey_TreeOnlyUnavailable`。
