### Web Frontend Rendering
- **⚠️ 新建/派生会话必须同时打开（或聚焦）该会话的 agent tab —— session-per-tab 下"切会话 = 切 tab"（2026-09-17「点侧栏『新建会话』，确认后侧栏新会话高亮了，但窗口没切过去，必须再点一下新会话」根治）。** desktop 主区 `AgentPanel` 的会话身份来自**它自己 tab 的 `params.sessionId`**（`useTabManager.openTab` 把 `data.filePath` → `PanelParams.sessionId`；逻辑键 `agent:<channel>:<chatID>` 保证同会话只聚焦不重复），**不是**全局 `activeSession`（只在 seed tab / 手机端无 sessionId 时回落）。因此 `store.createSession()` 内部的 `switchSession`（store activeSession + 后端 /switch）只更新**侧栏高亮**，主区当前 tab 依旧绑旧 sessionId → 「侧栏切了、窗口没切」。修法：创建成功后调 **`openAgentSessionTab(tabManager, chatID, channel, title)`**（`web/src/lib/sessionTabs.ts` —— 唯一入口，禁止各处再手写 openTab 字面量）。**所有「创建/派生新会话并切过去」的入口都要接**：desktop `core.sessions` 面板（`builtinPanels.tsx` 的 `NewSessionDialog onCreate`）+ 命令 `session.new`（`AppShell.tsx`）已接；fork（`onFork` → openTab）、会话列表点击（`handleSelect` → openTab + `activateSession`）本来就是这一模式。**手机端（`MobileAppShell` 的 `mobilePanelProps` 无 sessionId）不要调**：手机没有 dockview，`openTab` 只进 pending 队列静默丢失；手机端 AgentPanel 跟随 `activeSession`，所以「完成切换」= **关闭抽屉**（`onSessionSelected`，抽屉是 Modal 覆盖层，不关就等于"窗口没切"）。侧栏容器 `SessionSidebar`（现仅手机抽屉消费）用 `onSubAgentSelect` 判别两态（与 `handleSelect` 同一判据）：有 → 手机（关抽屉）；无 → desktop（`openAgentSessionTab`）。守护：`web/src/components/panel/builtinPanels.createSession.test.tsx` + `web/src/components/session/SessionSidebar.test.tsx`（mobile 关抽屉/不开 tab + desktop 开 tab）。
- **⚠️ Goal 实时链路（2026-09-05 "agent set goal complete 后前端样式不更新"根治）：goal 状态是【会话级】状态，与 todos 同模式经 TDSM 流转。** 完整链路：后端 `setGoalCompleteTool` 完成后**必须**调 `onComplete`（wired to `Agent.emitGoalProgress`，agent.go:1783）推 goal progress 事件（此前工具只调 `manager.Complete()` 零事件）；前端 `normalize.ts optGoal` 解析 progress 载荷的 `goal` 字段 → iteration/phase_done 事件 → `reduce.ts applySessionFields`（todos+goal 统一的会话级携带 helper，含 I5 重放丢弃路径——goal 事件 seq 低不丢）→ `ChatState.goal` → `liveProgressFromState` 输出 `goal`（无 live turn 也输出——turn 结束后 banner 保持）。**GoalBanner 样式（completed 绿色/删除线）读 `goal.status`**。新增事件字段是 optional（`goal?:`）——测试里现有事件构造零改动。
- **⚠️ 用户从 UI 编辑 goal / todos 必须【立刻】生效，不得等后端 push —— 乐观覆盖 = `usePendingEdit`（2026-09-12 用户报告"编辑 goal 按 Enter 后恢复编辑前内容、刷新才生效"，todos 同类）。** 根因（显示层三连）：① `AgentPanel` 的 `const goal = progressSnapshot.goal ?? goalOverride` —— 服务端快照（旧值）**压过**乐观覆盖（新值），用户立刻看到旧内容；② `useEffect(() => { if (progressSnapshot.goal) setGoalOverride(undefined) })` —— 只要快照有值（哪怕还是旧值）就把覆盖清掉；③ todos 根本没有乐观副本（设计上"只信 push"），push 延迟/丢失即回退。修复：`web/src/hooks/usePendingEdit.ts`（`usePendingEdit<T>(snapshot, equal)` + `goalEqual`/`todosListEqual`）—— `commit(value)` 记住**提交前的快照值** before；覆盖生效期间渲染覆盖值；**快照相对 before 发生变化**时才清除（push 收敛 → 服务端值；agent 第三方改动 → 服务端值；push 丢失 → 覆盖持续生效，刷新由 DB/GetActiveProgress 重新水合）。接线：`handleSetGoal`/`handleUpdateTodos`/`handleClearGoal` 成功后 `commitGoal`/`commitTodos`；`/goal <text>` 命令的乐观路径同源；`get_goal` RPC 的两次兜底水合（session 切换 / busy→idle 边沿）改写入 `fallbackGoal`（只补"快照缺失"，不参与覆盖语义）。**守护测试：`web/e2e/goal-todo-optimistic.spec.ts`**（3 例：无 push 时编辑 goal/todo 立刻可见 —— mock 刻意不回推 SSE；push 到达后仍是新值 + 第三方改动以服务端为准）。**教训：任何"用户刚提交的状态"在从组件 props/快照直接渲染时，都要先问"服务端什么时候才会告诉我"** —— 依赖 push 的 UI 在 push 丢失时必然回退。
- **⚠️ `interruptMode` 必须随 busy=false 自动重置（2026-09-05 "插话/排队 UI 不随 busy→idle 切换"根治）。** interruptMode 是 AgentPanel 的 useState，UI 元素键于它而【不看 busy】：placeholder（interruptMode 分支在 busy 之前）、发送按钮 violet 样式、Zap 图标——busy→idle 后残留 true 会让"插话 UI"永久滞留（用户在 idle 会话看到 violet 发送按钮+插话 placeholder），且排队消息会带 `interrupt=true` 发给 idle 会话；idle→busy 残留则跳过默认排队模式直接显示插话。修复：MessageInput `useEffect(() => { if (!busy && interruptMode) onInterruptModeChange?.(false) }, [busy, interruptMode, onInterruptModeChange])`。Test: MessageInput.test.tsx "auto-resets interject mode when the session leaves busy"。
- **⚠️ 上传进度 + 媒体插入 + 下载端点（2026-09-06 "粘贴文件卡住 spin 很久 + 上传成功后 tiptap 插入媒体"）。** ① **uploadFile 是 XHR**（fetch 无上传进度事件）——`onProgress(loaded, total)` 回调驱动乐观 chip 进度条（`PendingAttachment.uploading/progress`，上传中禁删）；`onUpload` 签名链路（api.ts → useChatMessages → AgentPanel → MessageInput）全程 `(file, onProgress?)`。② **上传成功插入编辑器媒体**：`insertUploadedMedia`（MessageInput）——图片 → `![name](/api/files/download?key=<encoded>&inline=1)`（tiptap Image 扩展 inline 渲染），其他文件 → `[name](/api/files/download?key=...)` 链接；alt 清洗 `[[\]\n]`。③ **/api/files/download**（web_file.go）——GET `?key=<upload_key>&inline=1` → 302 签名 URL；`inline=1` 走 `GetViewURL`（无 attname，`<img>` 内联渲染——attachment 语义会让浏览器下载而非显示），默认走 `GetDownloadURL`（attname 强制下载，XSS 纵深）；key 必须 `uploads/` 前缀（防任意对象探测）。④ **@tiptap/extension-image**（v3，inline:true）——markdown `![alt](src)` → image 节点（tiptap-markdown 双向序列化）；**行内 image 旁会出现 `img.ProseMirror-separator`**（PM 内部光标定位元素，prosemirror-view:2012）——E2E/测试断言用 `img[src*="/api/files/download"]` 过滤，不能裸 `locator('img')`。**⚠️ CSS 陷阱：separator 是「无 src + alt=""」的空 `<img>`，会被图片加载占位规则（`img[alt=""]` / `img:not([src])` 的 24×24 渐变方块）误伤**——粘贴图片后出现「小黑色正方形」、输入文字就消失（PM 移除 separator）。修复（index.css）：占位规则加 `:not(.ProseMirror-separator)`，另给 separator 一条 `width/height/min-*/margin/padding/border/background: 0 !important; opacity: 0` 的零尺寸不可见规则（**保留 `display: inline`**——光标定位需要行内盒，不要用 `display:none`）。守护测试 `web/src/index.test.ts`（断言两条选择器规则存在）。⑤ 发送路径过滤：attachments 只含完成态 chip（`!p.uploading && p.uploadKey`），canSend 同源。
- **⚠️ 附件引用绝不重复追加（2026-09-11 用户报告「web 粘贴图片后发送，图片变成两张」）。** 富文本编辑器在**上传完成时就把图片 markdown 内联插进内容**了（`MessageInput.insertUploadedMedia` → `![name](/api/files/download?key=<encoded>&inline=1)`），所以 `msg.Content` **本来就带这条引用**；而 `channel/web/web_inbound.go` 的 `appendUploadRef` 又无条件追加了一遍 → 同一条消息里出现两个 `<img>`（一个紧跟文字、一个单独成段）。修复：追加前先判重（`uploadKeyReferenced`：两种转义形态都查——前端 `encodeURIComponent` 把空格编码成 `%20`，Go `url.QueryEscape` 用 `+`；只比 `/api/files/download?key=<escaped>` 前缀，兼容 `&inline=1` 有无）。**REST（`expandUploadKeys`）与 WS（`web.go` 的 upload_keys 循环）共用同一个 `appendUploadRef`**，所以改一处两条路径都覆盖——新增上传相关代码务必复用该 builder，不要另写拼接。仍要保留「内容里确实没有引用时才追加」的行为（API 调用方 / 未内联的旧客户端 / 用户删了内联图但留着 chip）。Tests: `channel/web/web_inbound_expand_test.go`（`DoesNotDuplicateReferenceAlreadyInContent` 复现 + `StillAppendsWhenContentLacksReference` 反向守护）。
- **⚠️ 非图片附件的下载引用 = 单一实现 `uploadDownloadRef`，绝不把内部失败文案写进用户可见正文（2026-09-20 用户 P0：「本地静态存储下上传 15.gz，消息里出现 `📎 [用户上传文件: 15.gz] (获取下载链接失败)`」）。** 旧非图片分支直接调 `wc.ossProvider.GetDownloadURL(key)`：默认本地/静态存储（`LocalProvider`）**没有签名能力**（`GetDownloadURL` 恒返回 error）⇒ 错误分支把**内部文案拼进 content**——而文件其实**上传成功**（同一条消息里编辑器内联的相对下载链接是好用的）。图片分支不受影响（稳定相对 URL，见上一条）。修复：URL 解析收口到**单一实现** `WebChannel.uploadDownloadRef`（`channel/web/upload_ref.go`；REST `expandUploadKeys` 与 WS 循环共用 `appendUploadRef` 同一入口，改一处两条路径都覆盖）：云 OSS ⇒ provider 签名 URL；本地 static ⇒ `serverBaseURL()` + 相对路径的**绝对** URL；**拿不到 base URL 或签名失败 ⇒ 降级为稳定相对 URL `/api/files/download?key=…`（函数无 error、绝不返回错误文案）**。`serverBaseURL()` 解析顺序：`WebChannelConfig.PublicURL`（**只接受 http(s)**；`ws://`/`wss://` 跳过——同一字段也喂 runner 连接命令，不猜 scheme）→ `Start()` 后真实监听地址（通配绑定 `0.0.0.0`/`::` 映射 `127.0.0.1`，端口取真实绑定值）→ 配置 Host/Port（Port>0）→ `""`（降级相对 URL）。⚠️ 两个诚实标注：① 由此拼出的绝对 URL 指向同源 `/api/files/download`，**该端点 cookie 鉴权**（`authMiddleware`），DownloadFile 工具服务端直取不带 cookie 会 401 —— 这是下载端点既有语义（本轮未改，属工具侧可用性议题）；② 契约只保证「正文永不出现内部失败文案 + 引用永远可解析（绝对或相对）」。Tests: `channel/web/upload_ref_test.go`（6 例；修复前 5 红——local 无 base / local+PublicURL / local+listener（含 0.0.0.0 与 `[::]` 映射）/ 云签名失败降级 / ws:// 跳过 / 配置 Port 兜底）。
- **⚠️ tiptap 输入框（MessageInput）链接/上传四件套（2026-09-05 "链接不可见/文字吸入超链接/上传类型限制"根治）。** ① StarterKit v3 **内置 Link 扩展**（v2 没有），默认值是文档编辑器语义不是输入框语义：`inclusive()=autolink=true`（在链接尾部打字新文字自动并入链接——"意料之外的文字变成超链接"根因）、`openOnClick=true`（编辑中点链接新开标签页）、`linkOnPaste=true`、`shouldAutoLink` 默认接受裸域名（`file.tar.gz` 的 `.gz` 是合法 TLD → 文件名成链）。必须 `StarterKit.configure({ link: false })` + 定制 `EditorLink`（`MessageInput.tsx`：inclusive:false / openOnClick:false / linkOnPaste:false / shouldAutoLink 只认 `^(https?://|www\.)` / markdownLinks:true 实时成链）。② Tailwind preflight 把 `a` 重置为继承色——`.xbot-editor a` 必须显式 CSS（accent+下划线，index.css），否则链接与正文像素级一致（"看不见超链接"根因）。③ **上传类型零限制（用户指令 2026-09-05，不许加回白名单）**：`web_file.go` 的 `isAllowedExtension`/`isBlockedMIME` 已删除——任何类型可上传，仅保留 10MB 大小限制；前端粘贴/拖拽文件经 `editorProps.handlePaste/handleDrop` 自动上传（SelectionToolbar/BubbleMenu 见 channel.md）。④ PM 的 `selectionchange` 是**异步 task**——keydown handler 读 `editor.state.selection` 前必须 `view.domObserver.flush()`，否则同帧键击（Home→Ctrl+K）读到 stale selection（E2E 稳定复现）。测试坑：jsdom 合成 paste/drop 事件必须带 `getData:()=>''`（PM 内部 handler 先读它）+ drop 需 polyfill `document.elementFromPoint`；Playwright position-click 到块级 `<p>` 中心落在短文本右侧空白 → caret 在文本末尾 → 词选错（用 `Home` 键做确定性光标）。详见 `docs/agent/channel.md` "Web Frontend Message Composer"。
- **注入型（synthetic）通知工具的卡片渲染契约（2026-09-11）：`tools.SyntheticToolHints` 是唯一载体，走 `ToolHints` 通道（模型不可见）。** 后端把系统通知伪装成 tool-call 对注入 Run（`background_task_result` / `bg_subagent_completed` / `cron_fired` / `async_message` / `user_interrupt` / `user_cancelled` / `delivered_message` / `loop_detected` / `pre_turn_end`），以前前端只能把这些「假工具」原样当文本/JSON 显示。现在每个注入点在 `injectSyntheticToolPair`（engine_run.go）与 `backgroundNotificationSyntheticTool`（agent_process.go）里同时给两样东西：**`Summary` = 一句话标签**（卡片标题行）、**`ToolHints` = `tools.EncodeSyntheticToolHints(...)` 的 JSON**（`tools.BgTaskHints` / `SubAgentHints` / `MessageHints` 构造：`kind`/`task_id`/`task`（**原命令或原任务**）/`role`/`instance`/`status`/`exit_code`/`elapsed_ms`/`message`/`output`/`error`）。前端 `ToolRender.tsx` 的 `SyntheticToolCard`（`isSyntheticToolName` 派发，含 `bg_subagent_` 前缀）解析 `tool.toolHints` 渲染卡片：图标+标题+状态徽章+退出码+耗时+**Original task**+输出预览（>600 字符可展开）；`parseSyntheticHints` 返回 null 时回退到 `summary` 文本（兼容无 payload 的历史行）。⚠️ **三个必须遵守的点**：① `SubAgentBgNotify.Task` 必须由 spawn 点填（`msg.Content`）——否则子代理卡片没有「原任务」；② **图标一律用 lucide SVG，禁止 emoji**（emoji 在缺字体的环境渲染成方框，E2E 截图实测到 `□ Scheduled job fired`）；③ 已完成工具**由 `iteration_history` 携带并渲染**，`completed_tools` 不被 live 视图渲染（`chat/integrate.ts` 注释），所以 E2E 必须通过 `iteration_history` 注入。Tests: `ToolRender.test.tsx`（parse/card/legacy 回退）+ `web/e2e/synthetic-tool-cards.spec.ts`（pill→详情，断言原 task/输出可见）。

- **⚠️ 脏标记必须下沉到 chunk：长 turn 的每帧代价必须与 N 无关（2026-09-18 用户报告「高度估算算得慢 / async 计算导致抖动 / 理论上只要计算倒数的几十个迭代…应该快如闪电」根治）。** `TurnBody` 的窗口化渲染循环里 `invalidate()` 被 **ResizeObserver 的每一次尺寸变化**触发，而**流式期间尾部块每帧都在长高** ⇒ **每帧都是"脏帧"**；旧实现的"脏帧"是**整帧**语义 ⇒ 每个脏帧都为**全部 N 个迭代**跑 `mutedHeightFor`（查 tracker）+ 为每个 chunk 分配长度 = chunk 大小的 `heights` 数组（总分配 ≈ N）+ 全量 `collectPending` ⇒ 代价 ∝ turn 总长（"turn 越长越慢"，而窗口化后**真正影响画面的只有视口内那几十个块**）。**修复**：`keyToChunk`/`iterToChunk` 映射（重建 chunk 时登记）+ `dirtyChunks`；事件按身份精确标脏（IO→`invalidateIter(iteration)`、RO/settle/复核→`invalidateKey(hKey)`；映射缺失退化为整帧，**正确性不依赖映射完整**）；渲染循环 `itemsSame && !整帧脏 && !touchedChunks.has(c)` ⇒ **原样复用上帧元素**（React 在该子树直接 bail）；`turnID`/`heightScope` 变化清空映射 + 整帧失效。守护：`turnBodyDirtyScope.test.tsx`（N=200 + 一次尾部 RO ⇒ 重算 >0 且 ≤ 一个 chunk(64)；修复前 = 200 ⇒ 必红；⚠️ **手动触发 RO 回调必须包在 `act()` 里**，否则 React 更新不 flush → 断言恒 0 但**假绿**）+ 计数钩子 `__turnBodyDecisionCompute`。**注意**：估算（`estimateIterationHeight`）只用于**从未渲染过**的块，且**永不作为冻结依据** —— 这是"估算无法彻底避免"的边界（未渲染过的块没有真实高度可测，但可以**不让它影响可见区域**）。

- **⛔ 窗口化必须让"每帧元素数"与迭代数无关（2026-09-13 用户报告「turn busy 且该 turn 特别长（几千 iter）时手机必卡，切会话/刷新都没用」）。** 上一条窗口化只卸载了离屏块的**内容**，但**仍为每个迭代渲染一个外壳元素** —— 每个渲染帧照样 `contiguous.map(...)` 生成 N 个 React 元素，busy 流式每秒几十帧：N=3000 → **约 9 万元素/秒**的创建 + reconcile + GC，主线程被吃光。症状指纹：**busy 必卡、turn 越长越卡、刷新无效**（流还在继续）；闲置会话不卡（没有每帧渲染）。**正解 = 两 spacer 窗口化**：只渲染视口 ±1.5 屏的块，其余用**上下各一个 spacer** 占位（高度 = 未渲染块高度之和，实测优先、否则内容估算 × 本行标定系数；⛔ 依然禁止常数）。**必须同时关掉滚动锚定**：在消息滚动容器上加 `overflow-anchor: none` —— 窗口切换会改行内渲染内容，浏览器的滚动锚定会把 `scrollTop` 拽回原处（实测症状：`scrollTopAfter=30976`、回不到 0、顶部迭代不可见）。**验收**：E2E 4/4（含滚动稳定性 `scrollTopAfter=0` + `firstVisible=true`）+ busy 场景 N=10 与 N=200 的帧 p95/max 与节点数**同量级**；不许靠放宽断言变绿。

- **⚠️ 窗口化的「首帧竞态」：ref 回调先于观察器创建 → 首个 commit 挂载的块永不被观测（2026-09-13「加载的历史消息长了就卡 / 开侧边栏慢五六倍 / iter 特别多」根治，+13 行）。** 症状指纹：**只有「从 `/api/history` 首屏加载的 turn」卡**（loadMore 拉长历史后尤其），SSE 流式追加的 turn 正常；手机端开侧边栏慢 5-6 倍。根因：`register()`（`setRef` 回调）在 **commit 阶段**执行，而 `ResizeObserver`/`IntersectionObserver` 在其**之后**的 `useEffect` 里创建 —— 首个 commit 挂载的块 `observe()` 时 `roRef/ioRef` 仍是 `null`（落空），而 `setRef` 是 `useCallback([hKey, register])` **恒定引用** → React 不会二次调用它 → 这些块**永不被观测 → 永无实测高度 → 永不 settle → 永不 muted**。实测 40 turn×400 iter：**3200 块、muted=0**（全量挂载内容，每帧样式/布局/绘制代价 ∝ 迭代数）；同一份代码走 SSE 追加路径（effect 之后才挂载）则 400 iter → 395 muted ✓ —— **这条路径不对称是它长期漏网的唯一原因：所有既有 E2E 都走"流式追加"，永远测不到首屏加载路径**。修复（`TurnBody.tsx` 的观察器 effect）：观察器创建后**补观测 `elements.current` 里已注册的元素**（IO/RO 对同一元素重复 observe 幂等，初始回调自带当前尺寸）。实测（真实 Chromium + CDP CPU 4×、390×844；A=40×40，B=40×400）：节点 14559→**1392**（10.5×↓）、muted 0/1201→**1197/1201**、**开侧边栏 4646ms→450ms**（10.3×↓）、trace `UpdateLayoutTree` 4515.9→**363.7ms**（12.4×↓），滚动稳定性不变（`scrollTopAfter=0`/`firstVisible=true`）。守护（**先红后绿**）：`e2e/turn-iter-perf.spec.ts` 新增 `history-loaded long turn is windowed`（未修复时 `muted=0` 红）+ `turn_iter_perf_guard.test.tsx`（真实管线，已提交迭代流式帧渲染 0 且 N=20 与 N=200 相同 + 引用逐帧恒等）。**顺带证伪**「`backdrop-filter` 每帧重采样」假设：A/B/B′ 三组（blur ON→OFF→ON）证明重新开启 blur 后**依然快**，且移动端外壳下 `PanelChrome` floating 不渲染 → **不要动玻璃质感**。**已知未解决（诚实标注）**：① 流式期 long task 未降（15981→20821ms）——窗口化后 DOM 仅 1392 节点，说明流式抖动**不来自已提交迭代 DOM**，嫌疑转向 `stream_content` 每事件整表 re-render + 每帧 `scrollTop=scrollHeight` 强制布局；② 冻结复核是**每个新冻结 key 一个 400ms 定时器**（6000 块 ≈ 1.2 万次 render → long task 集中爆发），应批量/按屏调度。**教训：任何"靠观察器/副作用驱动"的优化，都必须有覆盖「首屏加载（首个 commit）」路径的守护测试** —— 只测增量（SSE 追加）路径会漏掉初始化竞态。

### Web Terminal (PTY)
- **PTY follows the session's runner, same as Shell tool.** `channel/web/web_pty.go:ptyManager.selectBackend(senderID, sessionKey)` resolves the session's sandbox via `tools.GetSandbox()` → `SandboxRouter.SandboxForSession("channel:chatID")`. `none` sandbox → `localPtyBackend` (PTY on web server via `creack/pty`). `remote` sandbox → `remotePtyBackend` (PTY on the runner via WS protocol). Docker mode on the runner uses `docker exec -it`.
- **PTY protocol mirrors the existing stdio streaming protocol.** `runnerproto` defines 6 message types: `pty_create` (req/resp), `pty_stdin` (fire-and-forget), `pty_resize` (fire-and-forget), `pty_close` (req/resp), `pty_data` (runner→server push), `pty_exit` (runner→server push). Runner-side `internal/runnerclient/pty.go:ptyManager` uses `pty.StartWithSize` + read loop; server-side `tools/pty_remote.go` routes pushes via `handlePtyPush` (called in `remote_sandbox.go` readLoop after `handleStdioPush`).
- **`PtyCreate` registers the stream before sending the request.** `RemoteSandbox.PtyCreate` calls `registerPtyStream` BEFORE `sendRequest`, so `handlePtyPush` can route `pty_data`/`pty_exit` pushes immediately. On failure, `removePtyStream` cleans up. `SetPtyHandlers` updates callbacks after `PtyCreate` returns (the web channel's `ptyManager.Create` calls `backend.Create` then `backend.SetHandlers`).
- **Multi-client broadcast + history replay.** `ptySession` holds `clients map[*ptyWSClient]struct{}` and a 64KB scrollback `history []byte`. New WS connections replay history, then receive live `broadcast` calls. WS disconnect removes the client but keeps the PTY alive (idle reaper kills after 5 min). Explicit `close` or PTY exit destroys the session.
- **`handleTerminalWS` uses cookie auth via `authMiddleware`.** The route `mux.HandleFunc("/ws/terminal", wc.authMiddleware(wc.handleTerminalWS))` — `authMiddleware` validates the cookie, then `handleTerminalWS` upgrades to WebSocket. The WS upgrade is GET, so `authMiddleware`'s body-size limit (only applied to non-GET) doesn't interfere.
- **Terminal API routes.** `POST /api/terminal/create` (body `{ chatID, cwd }` → `{ tid }`), `POST /api/terminal/{tid}/delete` (→ `{ ok: true }`), `POST /api/terminal/list` (body `{ chat_id }` → `{ terminals: [...] }`), `WS /ws/terminal?tid=<tid>`. All terminal routes use `authenticatedPOST`/`authMiddleware` (cookie auth). Chat delete calls `ptyMgr.CleanupChat(chatID)` to destroy all PTY sessions for the deleted chat.
- **`BackgroundPanel.tsx` uses xterm.js with incremental write.** Background task output (which contains `\r`, ANSI codes, progress bars) is rendered via `Terminal.write(output.slice(lastLen))` — only the delta since last poll is written, so `\r` (carriage return) correctly overwrites the current line instead of stacking as separate lines. The xterm instance is created once per panel mount and disposed on unmount.
- **Command hooks disabled by default** — requires `enable_command_hooks: true` in config.
- **Max 10 handlers per event**, total timeout 60s. Excess silently truncated with warning log.

## ⛔ 迭代历史**禁止任何有界化/截断**——缺 iter 就是 bug（用户 2026-09-21 定稿）

- **规则**：用户原话「**不能有任何 gap，任何 gap 都是破坏线性一致性**」「为什么我的 iter 还是缺」。一个 turn 的迭代历史必须**完整下发**（iteration 1..N 连续、无损）。**三处截断实现已全部删除，禁止复活**：
  - 服务端历史 `channel.BoundHistoryIterations` + `maxHistoryIterationsPerTurn = 60`（引入于 **`1b1f41e9`：`perf(history): 历史响应按 turn 尾部截断迭代（修「busy turn 迭代多 ⇒ 加载很久」）`，2026-09-15 smith**）
  - 服务端快照 `agent.maxActiveSnapshotIterations = 60`（引入于 **`5b43c212`：`perf(agent): active_progress 快照的 iteration_history 必须有界（切会话一次 11.2MB 的根因）`，2026-09-17 xbot agent**）
  - 客户端 `web/src/chat/normalize.ts` 的 `boundIterationTail` / `SNAPSHOT_ITERATION_LIMIT = 60`（引入于 **`1d6e98ff`：`perf(web): 快照迭代历史上限（客户端护栏）`，2026-09-17 xbot agent**）
- **为什么当年错了**：实测单 turn 最多 1,661 个迭代（≈3.6MB）确实让历史加载随迭代数线性变长 ⇒ 三处"压体积"各截一刀。代价是**用户直接看到迭代缺失**（生产取证：`turn-1-c` 的 `data-iter-range="60-119"`、**1..59 永久不见**），而且**没有任何取回通路**（全 history 搜索 `before_iteration` 零命中）。⚠️ 更糟的是多处截断会制造两个**不相邻**的窗口 ⇒ 拼接出 gap ⇒ 渲染层的线性一致性守卫只能在 gap 处截断（「历史停在旧位置 / 中间迭代不见 / 新迭代出现即消失」）——**这就是历次"iter 缺了"投诉的根因**。
- **性能归渲染层，不得以丢数据换体积**：`TurnBody` 迭代级窗口化（只挂载视口附近的块 + `contain: layout paint`，代价与迭代数解耦）+ `MessageList` 虚拟行。payload 体积若再次成为问题，用压缩/流式等**不丢数据**的手段解决。
- 守护（判别力：任一处加回截断 ⇒ 对应用例必红）：`channel/history_iterations_complete_test.go`（120 个迭代必须全量下发、`IterationsTruncated == 0`、1..120 连续）、`agent/active_progress_snapshot_complete_test.go`（FetchAll 500 个迭代必须完整且连续）、`web/src/chat/iterationBound.test.ts`（客户端不得截断：200 个全留）。

## Web 一致性暂态（切换/恢复）必须显示 loading，不得给不一致画面

- **⛔ `historyReady` 必须是【派生状态】，不能是可写 state —— 否则切会话会闪一帧「空 MessageList」（2026-09-18 用户报告「切换会话会闪烁一瞬间错误布局」）。** 旧实现：`useState(false)` + 在**异步 `reload()` 回调**里 `setHistoryReady(false)`。切会话那一帧：`chatID` 已变（`activeMessageCacheKey` 变了、`store.clear()` 已在渲染期执行 ⇒ `messages=[]`），但 `historyReady` **仍是上一会话的 `true`**（setState 还没跑）⇒ `AgentPanel` 的 `showLoadingScreen` 为 false ⇒ 渲染「空 MessageList + 输入框」（没有 loading、消息区空白）⇒ 下一帧才翻成 loading ⇒ 再下一帧才是内容 = 肉眼可见的错误布局闪烁。修法（`web/src/hooks/useChatMessages.ts`）：`const [readyHistoryKey, setReadyHistoryKey] = useState<string|null>(null)` + `const historyReady = readyHistoryKey === activeMessageCacheKey` —— key 随会话同步变化 ⇒ **同一次渲染**里就翻转，窗口为 0；写 ready 时用**本请求捕获的 `reloadKey`**（不是当前 `activeMessageCacheKey`），这样迟到完成的旧会话请求只会把「它自己」标 ready，不会把新会话误标 ready。守护：`useChatMessages.test.ts`「historyReady flips in the SAME render as the session switch」（记录每次渲染的 historyReady，断言切换后**第一次**渲染即为 false —— 不 waitFor；改回 setState 实现必红）。
- **⛔ 「会话只要开始切换就应该渲染 loading」还覆盖第二条路径：切 tab 进入一个【已存在】的面板（用户 2026-09-18 二次反馈，帧级 E2E 定稿）。** 该面板里存的是**上一次可见时**的快照；旧代码在重新可见时只 `reloadChat()`（后台对账）而**不回到 loading** ⇒ 先渲染旧快照、等对账回来再改写 = 用户看到的「一瞬间的渲染错误」（实测：切回已存在 tab 的整段对账期间**全程无 loading**）。修法：面板 `isVisible` false→true（= 一次新的会话激活）时先 `chat.markHistoryStale()`（重置 `readyHistoryKey`）+ reload，且**必须在 `useLayoutEffect`** 里（与"变为可见"同帧提交；用 `useEffect` 会先画一帧旧内容）。`markHistoryStale` **只**用于"新激活"——同会话后台 reload（resync/compaction）绝不重置（会让已渲染 live 消失）。守护：`web/e2e/session-switch-loading.spec.ts`（两例：新建 tab / 切回已存在 tab，切换后**第一帧**必须已是 loading 屏；含逐帧采样 + 页内时钟对齐，避免 Playwright actionability 延迟造成的假红）。

，不要先给"只有 live"的画面**（用户 2026-09-15：「切换一个 busy session，会有几秒只能看到 live iter，过了很久历史才出来，这是不对的」）。新渲染管线（`web/src/chat/useAgentChatState.ts`）**只 gate 了历史派发**（`if (!historyReady) return`），live 事件仍即时归约进 store ⇒ 若渲染层不加闸门，切到 busy 会话的瞬间 rows 就只有 in-flight 的 live turn，要等 `fetchHistory` 落地才补齐。修法（`AgentPanel`）：`chat.historyReady === false` 时渲染 loading 屏幕（spinner，`data-testid="session-loading-screen"`）代替 `MessageList`；**严格 `=== false`**（undefined/测试 mock 视为就绪，避免 loading 常驻）。注意与既有约定区分：**不得**用 `chat.loading` 做这个闸门（reload 也会置 loading，而 live 在 reload 期间必须继续可见）。

- **⚠️ loading 屏幕只在「确实有会话、历史尚未到达」时遮挡面板 —— 无会话时必须交出输入区**（2026-09-15 CI 事故）：`AgentPanel` 的闸门必须是 `(chat.historyReady === false && !!chatID) || resumeLoading`，**不能**只判 `historyReady`。原因：全新环境（E2E 的 fresh XBOT_HOME / 新用户）里会话树为空、`chatID` 为空，`historyReady` 恒为 false ⇒ 若只判 `historyReady`，面板会被 `Loading…` **永久盖住**，用户既看不到 "No sessions yet" 空状态、也无法输入/发送 ⇒ CI 的 `chat.spec` "should show user message after sending" 必红（Playwright 快照里侧栏是 `No sessions yet — create one from the top-right`、面板只有 `Loading…`）。

- **长时后台/锁屏恢复必须强制整屏重载（带 loading），不能只靠 SSE 增量追赶**（用户 2026-09-15：「手机锁屏半天再打开不会触发会话重新加载，SSE 追到最新但过程剧烈抖动 —— 不如展示 loading 屏幕」）。聊天 hook 里**原本没有任何 visibility/resume 触发器**（`visibilitychange` 只在 git-fancy 插件与 `useSessionStore` 的 HTTP 对账里）⇒ 恢复可见后只有 SSE 环缓冲重放 + live 反复改写 = 抖动。修法（`AgentPanel`）：`visibilitychange` 记录隐藏时刻，**隐藏 > 60s** 恢复可见时 `setResumeLoading(true)` + `reloadChat()`（DB 权威历史整屏重载），重载完成且已有消息后收起 loading；**< 60s 的短暂切走不重载**（避免打断正常使用）。守护：`src/workspace/panels/AgentPanel.test.tsx` + `src/components/agent/MessageList.test.tsx`（39 用例）。
- **⚠️ 锁屏恢复后 busy 会话必须从 `active_progress` 恢复 live —— 即使 DB 快照已把「在跑的 turn」折成 committed（2026-09-18 用户报告「手机端 busy 会话熄屏再打开：loading 后明明 busy 却看不到最新进度且不再更新」）。** 链路：熄屏期间 agent 继续跑，把中间 assistant/tool 行 + 已完成迭代的 `iteration_history` 增量落库 ⇒ 解锁时面板 `reloadChat()`（用户看到的那次 loading）拿到 DB 快照，`historyToReplaced` 把**仍在跑的 turn** 折成 `committed`（因为已有迭代）；而 `chat/reduce.ts` 的 `history_replaced` 第 3 步恢复 live 的条件原本只有 `!existing || isHollowFrozen(existing)` ⇒ `committed`（"跑了一半"的**常态**）被原样保留、`activeTurn` 保持 null ⇒ ① `liveProgressFromState` 返回 EMPTY（**看不到 live 进度**）+ ② 后续 iteration/stream 事件先被「committed 遮蔽」拦下（`ev.iter` 不大于已落库 maxIter 时 `return s`）⇒ **界面永久冻结**。修复：当 `ev.active`（与 history 同一次 fetchHistory 的**一致**快照；`phase ∈ {done,frozen}` 时 `historyToReplaced` 根本不会构造它，turn 结束后端还会删掉该快照）指向该 turn 时，**把它升级回 live**并设 `activeTurn`：迭代 `union`（DB 侧可能比快照更全——快照只保留尾部 `SNAPSHOT_ITERATION_LIMIT` 条），**同号以快照权威**（服务端 live 比 DB 增量行新，与第 3.5 步同向）。**判据：只有 `ev.active` 指向该 turn 才升级** —— 真结束（无快照）的 committed 绝不能被复活成 live（对照用例守护）。守护：`web/src/chat/p0-mobile-resume-live.test.ts`（3 例：DB committed + active ⇒ 必须 live 且后续事件继续更新 / 无 active ⇒ 保持 committed / 迭代 union + 同号快照权威；修复前 2 红）。

## ⛔ observer 被 cleanup 之后必须**彻底静默**（2026-09-23 CI 红根因：`ReferenceError: window is not defined`）

**症状**（CI Frontend job 红，但用例全绿 ⇒ 极易被误判为 flake）：

```
Test Files  160 passed (160)
Tests       1693 passed (1693)
Errors      1 error
##[error]ReferenceError: window is not defined
 ❯ resolveUpdatePriority  react-dom-client.development.js:1308
 ❯ dispatchReducerAction  react-dom-client.development.js:9102
 ❯ Virtualizer.notify     @tanstack/virtual-core/dist/esm/index.js:263
 ❯ wrappedCb              src/components/agent/MessageList.tsx:208
 ❯ @tanstack/virtual-core/dist/esm/index.js:84
```

**根因（虚测源码实证，不是概率问题）**：`@tanstack/virtual-core` 的默认 `observeElementOffset`
排了一个 `isScrollingResetDelay` 的 debounce 定时器，**它返回的 cleanup 只移除事件监听、
从不取消这个定时器**：

```js
const fallback = debounce(targetWindow, () => { cb(offset, false) }, isScrollingResetDelay)
...
return () => { element.removeEventListener("scroll", handler); ... }   // ← 没有 cancel
```

于是：**滚动 → 组件卸载 / 测试环境销毁 → 定时器仍触发 `cb(offset,false)` → virtualizer.notify
→ React setState → 读 `window`（jsdom 已销毁）→ `ReferenceError`** ⇒ 用例全绿但 vitest 进程
exit 1。本地 pre-commit 常绿（时序不同：本地 debounce 在环境存活时就烧掉了），**只在 CI 的
时序下爆** ⇒ 表现为"概率性"，实为确定性契约缺失。

**契约（修法）**：包装第三方 observer 时，cleanup 必须把「已销毁」变成硬状态 ——
`MessageList.tsx` 的 `rafCoalescedObserveElementOffset` 用 `let disposed = false`；
`wrappedCb` 首行 `if (disposed) return`；cleanup 里 `disposed = true` + 清 pending + 
`frameScheduler.cancel(flushTask)` + 调 default cleanup。这不是防御性编程，而是
**disposed 语义**：我们把 cb 交给第三方调度器，就必须保证销毁后对它的调用是 no-op。

**守护测试**：`web/src/components/agent/messageListObserverDisposal.test.ts`
（假定时器 + 真实 scroll 事件 + cleanup + 推进时钟 ⇒ 断言 cleanup 之后**零新增回调**；
另有一条"未 cleanup 时行为不变"的反向守护）。判别力：去掉 `disposed` 守卫即红。
