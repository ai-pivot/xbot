### CLI / BubbleTea
- **`CLIChannelConfig` is ALWAYS passed by pointer, NEVER by value.** `NewCLIChannel(cfg *CLIChannelConfig, ...)` stores the pointer; all later modifications (callbacks like `BindChatFn`, `GetActiveProgressFn`) are immediately visible to the channel. Passing by value (the old code) silently discards any wiring done after construction, causing nil callbacks at runtime. Tests must always initialize `config: &CLIChannelConfig{}`.
- **`BindChatFn` must be set before `NewCLIChannel`.** The wiring order matters because the channel stores the pointer. All other callbacks (GetActiveProgressFn, GetTodosFn, etc.) follow the same rule — set on `cliCfg` before passing to `NewCLIChannel`.
- **`parseKeyInput` with modifiers must NOT set `Text` field.** `Key.String()` returns `Text` if non-empty (ultraviolet `key.go:392`), bypassing `Keystroke()`. `{Code:'c', Text:"c", Mod:ModCtrl}.String()` → `"c"` not `"ctrl+c"`, breaking cancel.
- **Iteration snapshot deduplication**: PhaseDone + handleAgentMessage can both snapshot the same iteration. Always dedup by iteration number, preferring PhaseDone (has reasoning from server).
- **`ElapsedWall` must be set in ALL snapshot paths** — missing it causes total time to fall back to summing only last iteration's tool.Elapsed.
- **Remote TUI progress: WS now sends `protocol.ProgressEvent` directly** (no conversion). Adding new fields to ProgressEvent is sufficient — no separate WsProgressPayload or conversion functions exist anymore.
- **Cancel key must be `channel:chatID` only (no senderID).** Background task notifications inject messages with senderID="user", while CLI users have different senderIDs. Including senderID in the cancel key makes cancel impossible for bg-task-triggered turns.
- **Cancel interception must NOT send premature cancel ack.** The `/cancel` handler in the agent loop only sends the cancel signal to `cancelCh`. The cancel ack (with `cancelled=true` metadata) is sent exclusively by `chatProcessLoop`'s `wasCancelled` path AFTER Run returns. Sending it in the interception caused TUI to enter idle while the Run was still active — the cancel signal is asynchronous (consumed by `cancelListener` goroutine), so there was a window where TUI was idle but the agent was still working.
- **Cancel records pending bg notifications for the cancelled session.** `handleCancelledRun` takes same-session notifications still pending in `bgRunPending` and records them into the interrupted turn as synthetic tool observations; it also records a `user_cancelled` synthetic tool. Both the synthetic assistant and tool messages are marked `DisplayOnly=true` — they are persisted to DB for UI display but excluded from LLM context (`GetAllMessages` filters `display_only=0`). This ensures the next model call does NOT see the cancel marker, which is correct for graceful shutdown resume (the LLM should continue as if the cancel never happened). The model still sees partial tool calls/results (persisted by `IncrementalPersist` without `DisplayOnly`). Notifications already drained into the Run were already persisted by the normal synthetic-tool injection path, so cancel clears only their `drainedThisRun` tracking metadata. Other-session pending notifications remain in their own session bucket.
- **DrainBgNotifications is cancel-aware.** `engine_run.go` post-iteration drain checks `ctx.Err() == nil` before draining. If ctx is already cancelled (cancel signal arrived during the LLM call), drain is skipped so `handleCancelledRun` can record this session's pending notifications in the interrupted turn before the UI receives the cancel ack.
- **`wireBgNotificationDrain` tracks drained notifications.** Drain copies consumed notifications into `bgSessionState.drainedThisRun` (guarded by `drainedThisRunMu`). On normal/error turn completion, `clearDrainedThisRun()` discards the tracking metadata after notifications were processed. On cancel, `handleCancelledRun` clears the tracking metadata without re-delivering those already-persisted notifications as a fresh user message.
- **⛔ 迭代边界必须保留已渲染的工具 —— 新状态机（`chat/reduce.ts`）曾漏掉旧 store 的同款守卫（2026-09-18 P0 渲染回归）。** 用户报告：「一个迭代的工具执行完成后会从 **web 迭代历史**里消失，直到收到**下一个迭代的第一个新 SSE** 才重新出现」= 线性不一致（信息倒退）。根因：渲染早已切到新状态机，而 `progressStore` 的 *"ALREADY-RENDERED CONTENT NEVER DISAPPEARS … Keep activeTools/completedTools across the iteration boundary … would vanish until the NEXT structured event appends the history"* 守卫**没有一起迁移** —— `reduce.ts` 迭代分支的 `activeTools: ev.activeTools` 是**整表替换**，而迭代推进/commit 的边界事件常常不带该迭代的 `iteration_history` / `active_tools`（多为 `phase:undefined` 的流式 delta 或新迭代首个事件）⇒ 刚跑完的工具被清空，直到下一个携带 `iterationsDelta` 的事件到达才回来。（`LiveSnapshot` 也**根本没有 `completedTools`**，`integrate.ts` 硬编码 `[]` —— 后端 `completed_tools` 被 normalize 解析后从未进入 live 状态。）修复：边界（`advanced || committedNow`）且事件**不带**工具时，保留 prev 的已渲染工具并把在跑/生成/排队中的标记为 `done`（视觉"已完成"，不误导）；事件自带列表时以其为权威。**守护：`web/src/chat/reduce.test.ts` 的 `P0(2026-09-18): iteration boundary keeps already-rendered tools`（2 例，变异自证：改回 `activeTools: ev.activeTools` ⇒ ① 必红）。** 教训：**每次把渲染逻辑/状态机迁移到新管线时，必须把旧管线里的"不消失/不倒退"类守卫逐条迁移并留下判别性测试** —— 这类守卫是"用户看得见的语义"，不是实现细节。
- **⛔ 写事务边界由「跨 handle 原子性」决定，不能只看性能（2026-09-18 缩短写事务的教训）。** `withSplitHistoryWrite`（`storage/sqlite/history.go`）把读/校验放在**池上的只读连接**（**不持 SQLite 写锁**）、写事务在**首个 Exec 时才懒开**（短 `BEGIN IMMEDIATE`）：校验原子性由进程内写门 `db.writeMu` 保证（同进程内无交错可能），持锁时长从 **O(历史长度)** 降为 **O(写入行数)**，且校验失败路径不再开空写事务。**但 `db.writeMu` 是每 `*DB` 句柄的（不是每文件）**：`TestCrossHandleRewindCannotBeFollowedByStale{ContextEdit,Checkpoint}` 证明「句柄 A rewind 后，句柄 B 的**过期** context_edit / checkpoint 必须失败」这条不变量**依赖"校验与写在同一个 IMMEDIATE 事务内"** ⇒ `appendControlLocked`(context_edit) / `AppendContextSnapshot`(checkpoint) / `AppendMasks` / ask-answer **必须保持 `withImmediateHistoryWrite`**（回退这几类之前实测 2 例红）。**允许 split 的判据（等价性可证）**：① fn 无读；**或** ② replay 的每个校验都被写语句在 SQL 里**原子重做**（如 `appendAskQuestionWith` 的 `WHERE EXISTS(id) AND NOT EXISTS(pending)`；`AppendMasks` 只重做「存在」不重做「active」⇒ 不满足 ②）。守护：`storage/sqlite/split_write_test.go`（读阶段用独立连接 `BEGIN IMMEDIATE` 必须成功 = 读阶段不持写锁；纯读路径不留事务/连接；fn 错误原样传播）。
- **`drainAndProcessNotifications` batches all notifications into ONE user message.** All drained notifications are formatted and joined with `\n\n---\n\n` separators, then injected as a single `injectBgUserMessage` call. This avoids spamming the TUI with N separate messages and triggering N separate agent turns when multiple bg tasks complete simultaneously. **⚠️ 2026-09-18 P0 回归（用户报告）：该函数一度被改成「每条通知各自注入一条 user 消息」**（注释还自述"各自 turn_id、可在队列 tray 单独取消"）—— 一次突发 N 条 ⇒ N 条 user 消息：收尾 drain 一次性注入后，队列立刻开始跑第 1 条（busy=true），**其余 N-1 条卡在用户可见的排队 tray 里**（用户截图：`Next turn 83` + Turn 84–88），既不能立刻发出、也拿不到"一次处理完"。**契约不可动摇：一次突发 = 一条消息 = 一个 turn，通知永不进用户可见队列。** 守护：`agent/bg_notify_test.go` 的 `TestDrainAndProcessNotifications_{MixedTypes,ConcurrentSafety}` 断言「N 条 ⇒ 恰好 1 条含 N 段 + 无第二条」。**前端止血（同日）**：`StagingTray` 的 ⚡「立刻插入」（取消队列项 + 以 `interrupt` 重发 ⇒ 注入活跃 turn）改为按**可寻址性**（`msg_id` 存在）显隐 —— 通知行同样可用（原先 `!isNotification` 把通知行显式排除，而堆在队列里的恰好全是通知行）。
- **Turn-ID + `turn_started` event: atomic turn association (replaces InjectUserMessage side-channel).** `chatProcessLoop` generates a per-session monotonic `TurnID` (`bgSessionState.turnIDSeq`) for every dequeued message, stores it in `bgSessionState.activeTurnID` (atomic — `sendMessage` reads it from the Run goroutine), and emits a `turn_started` progress event (`Phase:"turn_started"`, `TurnID`, `TurnStart{Trigger,Content,RequestID}`) BEFORE `processMessage`. The TurnID propagates through `RunConfig.TurnID` → `StructuredProgress.TurnID` → every `ProgressEvent` (via `buildProgressPayload`) + stream callbacks + `emitBuiltinProgress`/`emitBuiltinProgressDone` + the reply `OutboundMsg.TurnID` (stamped by `sendMessage`). `injectBgUserMessage` NO LONGER calls `injectCLIUserMessage` — the notification user message is delivered atomically with the TurnID via the unified progress stream, eliminating the cross-goroutine race between `InjectUserMessage` (caller goroutine) and the turn's reply (`handleOutbound` goroutine). TUI `handleTurnStarted` (`cli_update_progress.go`) intercepts `turn_started` BEFORE the cancel guard; uses `turnStartedProcessed` flag to distinguish "first turn_started for this turn (adopt TurnID)" from "turn_started for N+1 before N's reply (finalize N, start N+1)". `handleAgentMessage` uses `msg.TurnID` (fallback `m.agentTurnID` for SubAgent/legacy) and only clears `streamingMsgIdx` when `turnID == m.agentTurnID` — a late reply for a previous turn must NOT clear the current turn's streaming slot. Web `useProgressStream` handles `turn_started` in the `progress_structured` case → `onInjectUserMessage` callback; the `text` event carries `turn_id` (from `WSMessage.TurnID`). Notification user messages render with a 🔔 badge + muted style (`isNotification` flag on `cliMessage` / `ChatMessage`).
- **`sendMessage` MUST prefer the caller-supplied `metadata["turn_id"]` over `getActiveTurnID` for the FINAL reply.** The progress/stream events are stamped with `RunConfig.TurnID` (authoritative), but `sendMessage` previously stamped the reply with `getActiveTurnID(qualifyChatID(chName,chatID))` which can return 0 (the reply lands on `turn_id=0`). Frontend `commitAssistant(0)` then creates a turn-0 slot while the REAL turn's live shell stays behind — an empty `turn-{N}-live` DOM row above the committed `seq-*` row (user report: "是不是容器写错了" — empty DOM). `handleRunOutput` must pass `sendMeta["turn_id"] = msg.Metadata["turn_id"]`, and `sendMessage` must parse it (fallback `getActiveTurnID` only for tool-initiated mid-turn sends).
- **`bus.OutboundMessage` MUST carry `TurnID`, and `Dispatcher` MUST forward it to `OutboundMsg`.** The final reply goes through the bus path (`sendMessage` → `bus.Outbound` → `Dispatcher` → `channel.Send`). Without `TurnID` on `bus.OutboundMessage`, the top-level `WSMessage.turn_id` is omitempty-omitted (0), and the turn_id only survives in `metadata.turn_id` (the `sendMeta` map). The frontend then reads the missing top-level `turn_id` as 0 → `commitAssistant(0)` + `commitStaleLives` re-commits the same reply as `seq-*-stale` (SAME content rendered twice, duplicate `data-index`). Fix both layers: backend carries `TurnID` end-to-end; frontend `text` handler falls back `textTurnID = msg.turn_id && msg.turn_id > 0 ? msg.turn_id : (Number(msg.metadata?.turn_id ?? '') > 0 ? Number(msg.metadata?.turn_id) : 0)` and passes `commitTurnID = textTurnID > 0 ? textTurnID : undefined` to `onAssistantComplete` (preserve undefined semantics for bang/slash commands). Test: `text event turn_id from metadata.turn_id`.
- **Frontend MUST ignore a DUPLICATE `turn_started` for the ACTIVE turn (`turn_id === store.lastTurnID`, trigger !== 'resume').** A spurious re-emission (SSE reconnect replay of the same turn, a notification turn_started arriving twice, backend re-send) re-runs the commit path: `commitLiveProgressAndReset` (lastIter=0) + `finalizedRef=true` → the finalizedRef guard then DROPS every subsequent progress_structured — the live turn vanishes permanently (user report: "最新 turn 不断消失又出现，好像每个新迭代一次"; debug E2E: iter1 visible → duplicate turn_started → NO-LIVE-ROW through iter2). The stale guard (turn_id < lastTurnID) does NOT cover the === case. AskUser resume legitimately reuses the same TurnID (continuation of the same turn) and is excluded. Fix: `if (p.turn_id === store.lastTurnID && p.turn_start?.trigger !== 'resume') return` in the `turn_started` branch of `useProgressStream`.
- **TurnID is allocated at QUEUE-ADMISSION time (not at dequeue), and REST `POST /api/message` returns it directly.** `agent.chatWorker.admitToMsgCh` allocates the per-session `TurnID` (via `ss.nextTurnID()`, except AskUser answers which are NOT pre-allocated) BEFORE pushing the message onto `msgCh`, writes it to `Metadata["turn_id"]`, and acks the transport with `bus.DeliveryResult{TurnID, Queued}` — the ack is DELAYED from the main loop to the chatWorker (the main loop's `case q <- msg` no longer acks). The web REST response therefore carries `turn_id` + `queued` (web_rest.go handleMessage) so the frontend can bind the optimistic user row without depending on `turn_started` (which may be lost/coalesced in SSE). `queued=true` means the chat was already busy (`len(msgCh) > 0 || ss.busy.Load()`) — the message will be handled after the current turn; the frontend shows a queued marker (cleared by `bindLastUserToTurn` on `turn_started`). **`bus.InboundMessage.DeliveryAck` is `chan bus.DeliveryResult` (NOT `chan error`)**. AskUser answer is a NEW turn: `chatProcessLoop` allocates a fresh `turn_id` via `ss.nextTurnID()` at dequeue time (agent.go:2914-2921) — it does NOT reuse `ss.activeTurnID` (reusing it merged pre/post-answer content into one assistant block). `admitToMsgCh` skips pre-allocation for answers (`ask_user_answered` metadata) so queued messages can't pollute the allocation; the REST ack therefore carries `turn_id=0` and NO `user_echo` is emitted for answers — the frontend binds the answer row via `turn_started`. ✅ **Fixed (AskUser overhaul): the engine's incrementally-persisted intermediate messages now carry the run's TurnID** — `NewPersistenceBridgeWithTurnID(sess, count, cfg.TurnID)` (engine_run.go) stamps `persistMsg.TurnID = b.turnID` in `pendingMessages` (only when 0), and `buildWaitingUserOutbound`'s empty assistant stamps `msg.Metadata["turn_id"]`. Without the stamp, the answer's user row (turn N+1) sits AFTER turn N's intermediate rows in append order, so `deriveTurnIDs` Pass 2 (channel/subscription.go:583) mis-derives turn N's rows as N+1, and `ConvertMessagesToHistoryWithIterations` emits a forged assistant row carrying turn N+1's full iterations BEFORE the answer user row — duplicated/misaligned history rendering. Also: `AppendAskAnswerWithUserMessage` (storage/sqlite/history.go) atomically writes the ask_answer control + answer user row in ONE immediate transaction (crash consistency). CLI/RPC (`send_inbound`) never sets DeliveryAck — unaffected. `enqueueInbound` waits for the ack WITHOUT selecting on `ctx.Done()`: once handed off, the message IS processed — returning context.Canceled would tell the frontend the send failed, triggering a same-ID retry that the dedup layer silently swallows (losing the message).

- **`handleProgressMsg` 的 cancel guard 清除逻辑必须在 guard 的 return 之前。** 旧代码把"清除 turnCancelled"放在 `if m.turnCancelled && Phase != "done" { return }` 之后 → 永远不可达（死代码）。用户 Ctrl+C 后 `turnCancelled=true`，新 turn 的所有 progress（stream + structured）被 guard 阻塞 → 打字机失效、工具进度不可见、指令看起来无法处理（agent 报告 Bug #1/#5 cancel 死锁）。修复：清除逻辑移到 guard 前（`m.turnCancelled && Phase != "done" && m.typing` → 清除；turn_started 的权威清除可能被 coalesceProgress 吞没，typing fallback 兜底）。`finalizeTurnFromSnapshot` 恢复 `turnCancelled=true` 是**必要的**（防止 cancel 后 stale progress 触发 auto-start）——死锁由清除逻辑前置解决，不是靠不恢复。
- **CLI 三层 isStreamOnly 分类必须一致（`Phase==""`，不能用 `Iteration==0`）。** 后端 delta push 事件（`streamContentFunc`）`Phase==""` 但 `Iteration=当前迭代>0`。三处必须统一：(1) `SendProgress` 的 progressSlot 分类（cli.go）；(2) `coalesceProgress` 的 `bStructured`（cli.go，`Phase!=""`——旧 `|| Iteration>0` 会把 delta push 误判为 structured → 覆盖真正 structured 事件的 Phase/ActiveTools/CompletedTools/Content，工具标签消失）；(3) `handleProgressMsg` 的 `isStreamOnly`。另：`coalesceProgress` 必须合并 `StreamDelta`/`ReasoningStreamDelta`（否则 asyncCh 合并时增量丢失 → 打字机缺字）；progressSlot stream-only 合并时 delta push 事件**不回填** `old.StreamContent`（回填旧值会覆盖 cur 的更长累积 → 丢失/双重计数）。
- **`sendToAgent` 的 LLM 配置检查必须与 `sendMessage` 一致（仅 `sendInboundFn == nil` 时检查）。** 无条件检查 `cachedModelName == "" && hasNoSubscription()` 会在远程模式（`sendInboundFn != nil`）误拦截所有透传命令（/context、/new、/usage、/set-llm、/models 等）——自举悖论：需要配置 LLM 才能使用配置 LLM 的命令（agent 报告 Bug #1）。
- **`endAgentTurn` 必须设置 `inputReady=true`。** typing=false 后若 inputReady 保持 false，用户无法输入直到 handleAgentMessage/finalizeTurnFromSnapshot 到达（会话切换后 processing=false 但 inputReady 卡住，agent 报告 Bug #4）。
- **CLI 必须处理 `StreamDelta`（delta push 增量文本）——否则打字机失效（消息结束后才显示）。** 后端 delta push 协议（engine_wire.go `streamContentFunc`）在流式文本是前缀扩展时只发 `StreamDelta`（增量），全量只在 reset/out-of-order 时发。CLI 曾完全没处理：(1) `handleProgressMsg` 的 `isStreamOnly` 判断不含 `StreamDelta` 且要求 `Iteration==0`——StreamDelta 事件（`Iteration`=当前迭代>0）被误分类为 structured → 走 `applyProgressSnapshot`（也不处理 StreamDelta）→ 增量被忽略；(2) progressSlot 合并（stream-only→structured）不处理 StreamDelta → 丢失。修复：`isStreamOnly` 含 `StreamDelta`/`ReasoningStreamDelta` 且去掉 `Iteration==0`（`Phase==""` 已足够区分）；stream-only 分支把 `StreamDelta` 追加到 `cur.StreamContent`；progressSlot 合并把 `StreamDelta` 追加到 structured 快照的累积 `StreamContent`。Test: `TestHandleProgressMsg_StreamDeltaUpdatesTypewriter`。
- **`dedupConsecutiveAssistants()` is the rendering-level guard** against two adjacent Assistant blocks. Called by both `appendNewMessagesToCache` and `fullRebuild`. Two cases: (1) SAME turnID → merge content+iterations; (2) DIFFERENT turnID + first is `isPartial=true` → remove the stale placeholder. Case 2 covers ALL `isPartial` messages (empty or with baked content/iterations from `finalizeTurnFromSnapshot`), not just empty placeholders. The old `upsertMessageByTurn`/`dedupMessagesGuard` O(N) per-frame scans were deleted — `dedupConsecutiveAssistants` is O(n) but only runs on cache rebuild, not every tick.
- **`startAgentTurn()` calls `finalizeStaleStreamingBeforeNewUserMessage()` internally.** This covers all paths that bypass `sendMessage`/`sendToAgent` (auto-start, bg task injection, `/compress`, `cliProcessingMsg`, AskUser callback). Without this, `endAgentTurn`'s preserved `streamingMsgIdx` leaves the old assistant as `isPartial=true`, and `startAgentTurn` appends a new one right after it → two adjacent Assistant blocks. Callers that already called `finalizeStaleStreamingBeforeNewUserMessage` hit the early return (`streamingMsgIdx=-1`), no side effects.
- **`endAgentTurn` does NOT clear `streamingMsgIdx` or `progressState`.** Keeping `streamingMsgIdx` valid ensures the tick handler uses `updateStreamingOnly` (streaming path) instead of `appendNewMessagesToCache` (which caches incomplete content → flicker). Progress state (`iterations`, `current`, `reasoningByIter`) is preserved for flicker-free rendering between PhaseDone and handleAgentMessage. It is cleared by `startAgentTurn` → `resetProgressState` when the next turn begins, or by `handleAgentMessage` when the reply arrives. `handleAgentMessage` sets `streamingMsgIdx = -1` and calls `rerenderCachedMessage` for a single clean transition.
- **`isPartial` fallback checks `findMessageByTurn` before creating new message.** When `streamingMsgIdx` is stale (cleared by endAgentTurn), the fallback now searches for an existing message with the same turnID+role and reuses it, instead of appending a duplicate.
- **Cache generation counter (`histGen`/`allLinesGen`) prevents stale `allLines` reuse.** Every site that modifies `histLines` calls `bumpHistGen()`. The tick fast path only reuses `allLines` when `histGen == allLinesGen`. This replaces the old length-only comparison (`histLen == allLinesHistLen`) which could not detect content changes when line count coincidentally matched — causing stale cache + new content to render together as duplicates.
- **`turnDoneFlags` tracks per-turn completion state**: `doneProcessed` (PhaseDone created tool_summary) and `replyReceived` (handleAgentMessage appended assistant reply). `handleAgentMessage` checks `doneProcessed` to skip redundant tool_summary creation. **Cleared on session switch** in `postRestoreSessionSetup` to prevent stale flags from causing premature queue flush.
- **Queue flush requires `replyReceived` or `doneProcessed+turnCancelled`.** The old heuristic (`!typing` on next tick) could flush before the assistant reply arrived. Now the tick handler waits for `replyReceived=true` on the completed turn. A 2s timeout fallback prevents permanent queue stalls when replies are lost.
- **`flushMessageQueue` MUST NOT use the textarea as a send intermediary.** The old code did `textarea.SetValue(msg.content)` → `sendMessageFromQueue()` (which reads the textarea then `Reset()`s it) — this CLOBBERS the user's in-progress input draft. User scenario: send msg1 (agent busy) → send msg2 (queued, textarea cleared) → start typing msg3 → msg1 finishes → flush msg2 → msg3 is wiped. Fix (cli_turn.go): `flushMessageQueue` sends `msg.content` DIRECTLY via `sendMessage(msg.content)` — never touches the textarea. `sendMessageFromQueue` was deleted (only caller was flushMessageQueue). Regression test: `TestFlushMessageQueuePreservesInputDraft`.
- **`pendingToolSummary` is no longer used for PhaseDone→handleAgentMessage handoff.** The upsert-by-turn mechanism replaces it — `handleProgressDone` creates the tool_summary via upsert, and `handleAgentMessage` either finds it already there (doneProcessed) or creates it from local iteration history.
- **Cancelled turns must bake iterations into the streaming message BEFORE `endAgentTurn` clears `iterationHistory`.** The cancel path in `handleProgressDone` copies `iterationHistory` into `streamingMsg.iterations` before calling `endAgentTurn()`. Without this, all tool tags and reasoning rendered inline during the cancelled turn vanish after Ctrl+C. The cancel ack in `handleAgentMessage` also finalizes (not removes) the streaming message when it has iteration data — even if `content == ""` (e.g. agent was mid-tool with no text yet). Only truly empty messages with zero iterations are removed.
- **Turn completion uses `rerenderCachedMessage` instead of `fullRebuild`.** When the complete reply arrives in `handleAgentMessage`, instead of setting `rc.valid = false` (which forces O(N) `fullRebuild` → flicker), call `rerenderCachedMessage(completedMsgIdx)` which truncates the render cache back to that message and re-renders only it via `appendNewMessagesToCache` — O(1 message) instead of O(N). The cancel ack path uses the same mechanism via `cancelledIdx`.
- **`endAgentTurn` must NOT clear `streamingMsgIdx`.** Clearing it causes the subsequent `relayoutViewport→updateViewportContent` to call `appendNewMessagesToCache` and cache the streaming message with incomplete content (reply hasn't arrived yet). This forces a second viewport update when `rerenderCachedMessage` runs, causing double-flicker. Instead, keep `streamingMsgIdx` so `updateViewportContent` uses `updateStreamingOnly` (streaming path) — the message is NOT cached prematurely. `handleAgentMessage` will set `streamingMsgIdx = -1` and call `rerenderCachedMessage` for a single clean transition.
- **`snapshotIterationChange` falls back to `ReasoningStreamContent`.** When an iteration changes and the previous iteration's reasoning hasn't been finalized (structured `Reasoning` is empty, `reasoningByIter` missed it), the snapshot would lose the reasoning block — causing it to briefly disappear during streaming. The fallback (`prev.ReasoningStreamContent`) captures the live-streamed reasoning, matching the pattern already used in `handleProgressDone`'s cancel path.
- **Server-side cancel barrier via `ctx.Done()`** prevents stale progress events from arriving after Ctrl+C. `buildMainRunConfig` wraps every `ProgressEventHandler` with `select { case <-ctx.Done(): return; default: }`. When `/cancel` triggers `reqCancel()`, the ctx is cancelled, and all subsequent progress event handler calls return immediately — no stale progress/PhaseDone events leak through to trigger re-renders. No extra fields needed: the ctx is the natural cancellation mechanism already wired through `chatProcessLoop → processMessage → buildMainRunConfig`.
- **History handlers share unified dedup via `dedupAppend`.** `handleSuHistoryLoad` and `handleHistoryLoad` both dedup-append incoming messages using `msgIdentity{role, timestamp}` (keyed on role + timestamp, NOT turnID — `protocol.HistoryMessage` from DB has no turnID, so including it would make the same logical message dedup differently by source). `handleHistoryReload` still does overall replace (not append) via `mergeMessagesPreservingCache`. All three convert `protocol.HistoryMessage → cliMessage` via the shared `toCLIMessage` helper to prevent copy-paste drift. Prevents double-rendering when history reload races with in-flight messages.
- **`compressionReloading` and `turnDoneFlags` are cleared in `postRestoreSessionSetup`.** Without clearing, a stale `compressionReloading=true` from the previous session permanently blocks auto-start in the new session, and stale `turnDoneFlags` can cause premature queue flush.
- **`HistoryCompacted` handler MUST return early, skipping `snapshotIterationChange` and `updateViewportContent`.** The handler clears `progressState.iterations=nil` and `lastIter=0`, but without `return`, execution falls through to `snapshotIterationChange(msg.payload, prev)` where `prev` (captured before the handler) holds pre-compression data. The mismatch path (`prev.Iteration != lastIter(0)`) creates a stale snapshot from pre-compression state, polluting iteration history. After compression, there is no useful `prev` data — the async reload rebuilds everything from DB. The handler MUST `return` after `reloadMessagesFromSession(true)`.
- **`handleHistoryReload` MUST preserve the streaming message for ALL reloads, not just non-forceFullRebuild.** The old `!msg.forceFullRebuild` check meant forceFullRebuild (from compression) replaced messages WITHOUT preserving the streaming message. Combined with `compReloading` blocking auto-start, this left no streaming message at all. Now always preserves `streamingMsg` when `m.typing && m.streamingMsgIdx >= 0`.
- **`reloadMessagesFromSession` MUST use blocking send with timeout, NOT silent `default` drop.** The old `select { case ... asyncCh <- msg: default: }` silently dropped the reload when asyncCh was full (256 buffer). There was no retry — the comment "next progress event will retry" was false. Now uses blocking send with 10s timeout.
- **`liveIterationBlocks` deduplicates tools by `Name + Label`** — but `generating` tools skip dedup. Streaming tools have no labels yet (args still being generated), so two same-name tools (e.g. two `Read` calls) would share the same `Name+""` key and the second gets dropped. Fix: `Status=="generating"` tools are appended unconditionally, bypassing the `seen` map.
- **`liveIterationBlocks` MUST suppress pulse when any tools are present.** `hasSpinner` was only set for `running`/`active` tools. When a tool transitions to `done`/`error`/`pending` (between sequential tool execution), `hasSpinner` goes `false` → pulse spinner appears (+1 line) → next tool starts running → pulse disappears (-1 line). This H→H+1→H oscillation is the visible jitter. Fix: `if len(tools) > 0 { hasSpinner = true }` — pulse is an idle indicator for the thinking phase only, not for tool execution phases.
- **`snapshotIterationChange` data mismatch path now creates a snapshot instead of discarding.** When `prev.Iteration != m.lastSeenIteration`, instead of skipping the snapshot entirely (which permanently loses iteration data), it creates a snapshot tagged with `prev.Iteration` after checking it wasn't already snapshotted.
- **`progressState.current` is rendering data, NOT a state flag.** Busy/idle state is determined solely by `m.typing` (set by `startAgentTurn`, cleared by `endAgentTurn`). Using `progressState.current != nil` as a busy indicator causes the TUI to stay stuck in busy state after turn completion — `endAgentTurn` preserves `progressState.current` for flicker-free rendering, so it's never nil after a turn. All status bar, tick handler, and update-notice suppression checks must use `m.typing` only.
- **`updateStreamingOnly` MUST skip liveLines when `!m.typing`.** `endAgentTurn` preserves `progressState.current` and `progressState.iterations` for flicker-free rendering between PhaseDone and `handleAgentMessage`. But `updateStreamingOnly` renders BOTH `completedLines` (from `progressState.iterations`, which includes the final iteration with Content + Reasoning) AND `liveLines` (from `progressState.current`, which has the SAME Content + Reasoning). This causes the final reasoning + response to appear twice. For CLI sessions this is momentary (`handleAgentMessage` clears `streamingMsgIdx` shortly after), but for non-CLI sessions (`/su` to feishu/web/qq), `handleAgentMessage` never arrives → `streamingMsgIdx` stays valid → `updateStreamingOnly` runs every tick → persistent duplication. Fix: the `liveLines` rendering block guards with `m.typing` — when the turn has ended, only completed iterations are rendered (they already contain the final content).
- **`postRestoreSessionSetup` MUST call `refreshCachedModelName()` for LLM state resolution, NOT inline `LoadSessionLLMState` + `GetDefault` fallback.** The old code had its own LLM resolution path (local JSON → GetDefault) that bypassed the DB tenants table. In remote mode, `SaveSessionLLMState` passes `skipBackendFields=true` (local JSON never writes subID/model), so `LoadSessionLLMState` always returned zero → `GetDefault("")` returned the subscription's default `Model` (often `""`), overwriting the correct per-session model that `restoreSession()` had just restored from `savedSessions`. This only affected the default session (non-default sessions write local JSON via `SaveSessionLLMState` without skip at creation time). Fix: `postRestoreSessionSetup` now calls `refreshCachedModelName()` which checks DB tenants table (`GetSessionSubscription` RPC) first, then local JSON, then savedSessions, then GetDefault — the same 4-level priority chain used at startup. Context limits are then resolved from the now-correct `activeSubID` + `cachedModelName` via `ResolveEffectiveMaxContext`/`ResolveEffectiveMaxOutputTokens`. This makes default sessions and regular sessions follow the exact same restoration path.
- **`ensureSessionModel` auto-binds a model to ALL new sessions on first use.** Both `ResolveLLM` (agent side, covers all channels including Web/Feishu) and `postRestoreSessionSetup` (CLI side, for immediate status bar display) call auto-bind when a session has no per-session binding in the tenants table. Priority: Balance tier config (`user_settings["tier_balance"]` → `"subID|model"`) → last-used model (`user_default_model` table). The binding is persisted via `SelectModel` (writes to both tenants table and `user_default_model`), so subsequent calls hit the tenants table directly and skip auto-bind. If neither Balance tier nor last-used model exists, no binding is created (the caller falls through to system default). This ensures ALL sessions — CLI-created, `/chat new`, `/su` switch, Web/Feishu — get an explicit model binding on first use, not just those created via the CLI session panel. CLI's `ensureSessionModelBinding` is idempotent: it checks `GetSessionSubscription` first and returns immediately if the session already has a binding.
- **创建会话支持可选 `model` 参数（显式模型绑定，优先级高于 `ensureSessionModel`）。** Web `POST /api/chats/create` body 可带 `model`（模型名）；`ChatCreate` 回调签名 `func(senderID, label string, canonicalUserID int64, model string)`。后端逻辑（`serverapp/callbacks.go`）：有 `model` → `LLMFactory.ResolveSubscriptionForModel(senderID, model)` 找到提供该模型的 subscription → `SelectModel` 绑定新会话（解析/绑定失败非致命，warn 后 fall back 到 `EnsureSessionModelBinding`）；无 `model` → `EnsureSessionModelBinding`（Balance tier 优先，即"没这个参数默认 balance tier"）。Web 前端 `createSession(label?, workPath?, model?)` **默认继承当前 active 会话的模型**：未显式传 `model` 时通过 `get_context_usage` RPC 读当前会话模型名，仅当获取失败/无 active 会话时 model 为空（后端 fall back Balance tier）。`CreateChat` tool（agent 创建 SubAgent 会话）同样支持 `model` 参数（具体模型名），优先级 `Model > ModelTier > role.Model > "balance"`，group 类型应用于所有成员。
- **流式推送默认全量（`agent.delta_push` flag 默认 false），delta push 已废弃为可选。** delta push（#222 增量文本）引入多个可靠性问题：stateless gap 不恢复（打字机缺字）、三层 isStreamOnly 分类不一致（工具标签消失）、迭代边界前缀判断（前端清空 vs 后端不重置）、服务器重启拼接。还原为**每次推送完整累积文本**（`engine_wire.go streamContentFunc/streamReasoningFunc`：`a.deltaPush=false` 时总是发 `StreamContent`/`ReasoningStreamContent` 全量，`iter` 直接用）。前端/CLI 的 StreamDelta 处理**保留但不触发**（向后兼容，不删代码）。显式开启 `config delta_push: true` 才走 delta。Test: `TestStreamContentFullPush_Default`（前缀扩展也不发 delta）。
- **Delta Push + Watermark Pull protocol replaces full-history push.** Structured progress has ONE channel-agnostic producer (`buildProgressEventHandler`): build one `protocol.ProgressEvent`, attach the iteration delta once, store the snapshot once, then broadcast an isolated clone of that semantic event to every `channel.ProgressSender` (CLI/Web/plugin). Channels are transports only — never derive their own history or add channel-specific reducers. `ProgressEvent.Seq` is the semantic log watermark used by reconnecting clients; SSE/WS envelope seq is transport-only. Clients install active snapshots, ignore events with `seq <= snapshot.seq`, and NEVER synthesize completed iterations locally. Push events carry ONLY the newly completed iteration as `IterationHistory` (0 or 1 entries) — not the full cumulative history. `attachIterationDelta` (formerly `recordIterationAdvanceAndAttachHistory`) calls `recordIterationSnapshot` which returns the delta (the previous iteration snapshot) or nil if no advance. `GetActiveProgress` gains a `fromIter` watermark parameter: it filters `iterationHistories` to only return iterations with `Iteration > fromIter`. The CLI sends `m.progressState.lastIter` as the watermark. Tick pull frequency reduced from 100ms to 2s (every 20th tick) — it's now a safety net for recovering iterations lost to progressSlot coalescing or WS disconnect, not the primary delivery path. Push events are the primary path. `restoreIterationsFromSnapshot` changed from count-based replace to per-iteration append-with-dedup (`slices.ContainsFunc` by iteration number). `coalesceProgress` merges delta slices via `mergeIterationDeltas` (concatenate + dedup by iteration number). `/su` switch and initial restore pass `fromIter=0` to get full history (one-time operation). Web callback passes `fromIter=0` (web doesn't use delta protocol). `recordIterationSnapshot` now returns `*protocol.ProgressEvent` (the delta, or nil) instead of being void.
- **`startAgentTurn` MUST set `progressState.current` AFTER `resetProgressState`, not before.** `resetProgressState` clears `progressState.current` to nil. If the "thinking" initial state is set before `resetProgressState`, it gets wiped — the first tick sees `hasIterData=false` in `updateStreamingOnly`, falls back to `renderMessage` (empty content, no pulse spinner), and the user sees no visual feedback until the first structured progress event arrives (seconds later). Setting `progressState.current = {Phase:"thinking"}` after `resetProgressState` ensures `liveIterationBlocks` renders a pulse spinner on the very first tick — immediate visual feedback.
- **`mergeSubAgentTrees` MUST be called in `applyProgressSnapshot` before replacing `progressState.current`.** Structured events don't always carry SubAgents (engine only includes them when `resolveSubAgents` returns non-empty). Without merging, the tree flickers — appears when SubAgents are present, vanishes when the next structured event omits them. The merge preserves prev's running agents and marks dropped ones as done. `mergeSubAgentTrees` also preserves children when `new.Children` is empty but `prev.Children` exists (marks all prev children as done via `markAllDone()`). Without this call, `mergeSubAgentTrees` is dead code (only called in tests).
- **`finalizeTurnFromSnapshot` MUST create synthetic assistant message for ALL non-CLI channels.** The old code only did this for `m.channelName == "agent"` (SubAgent viewer). But when CLI `/su` switches to any non-CLI session (feishu, web, etc.), the agent's outbound reply goes to the originating channel via `sendMessage(chName, ...)`, NOT to the CLI channel. The CLI receives progress events (including Content via structured progress) and PhaseDone, but never receives `cliOutboundMsg`. Without the synthetic message, the CLI stays stuck showing "..." after PhaseDone. The fix: `m.channelName != "cli"` (covers agent, feishu, web, etc.). Content comes from `cur.Content` (set by `structuredProgress.Content` via `notifyProgress` before PhaseDone). PhaseDone payload itself has no Content — must fall back to `cur` (captured before `endAgentTurn`).
- **`ProgressEventHandler` MUST be created for ALL channels, not just cli/web/ProgressSender.** `buildMainRunConfig` previously only created `ProgressEventHandler` for `"cli"`, `"web"`, and plugin `ProgressSender` channels. When a CLI user `/su` switches to a feishu (or other non-cli/web) session and sends a message, the message's `Channel == "feishu"` → no `ProgressEventHandler` → `progressFinalizer`'s PhaseDone event is silently dropped → `finalizeTurnFromSnapshot` never runs → `m.typing` stays `true` forever (TUI stuck in busy). Fix: the `switch channel` in `buildMainRunConfig` now has a `default` branch that creates a `buildCLIProgressEventHandler(chatID, channel)` for non-cli/web/non-ProgressSender channels. This ensures PhaseDone, structured progress, and `lastProgressSnapshot` storage work for ALL channels when viewed via `/su`. Additionally, the `else` branch of the `ProgressNotifier` setup now sets a no-op notifier for non-cli/web channels without `autoNotify`, enabling `progressFinalizer` to generate PhaseDone events.

### CLI Rendering Panics
- **All render bodies (`renderGlobBody`, `renderShellBody`, `renderReadBody`, etc.) must use `ansi.Truncate`, NEVER manual `runes[:maxW-N]`.** On narrow viewports, `maxW-N` goes negative causing `slice bounds out of range [:-1]` panic. Glob and Shell both had this pattern — fix one, grep for the other. `ansi.Truncate` handles negative/zero widths safely.

All other channel files (feishu.go, mermaid.go) already use package-level vars — follow the convention.
- **`currentTheme` writes must be guarded when called from non-BubbleTea goroutines.** `ApplyTheme()` is exported and can be called from plugin/settings handlers. `setTheme()` now holds `currentThemeMu` — any new write path to `currentTheme` must also acquire this mutex.

### CLI Rendering Performance
- **Tick path must use direct line array assembly, not `setViewportContent` string path.** `histLines` + `dynamicLines` (rewind/dynamic part) are assembled in-place into the reused `allLines` slice and passed to `viewportSetLinesBypassMaxWidth`. This avoids O(total_content) string concatenation + O(N_iters) `lipgloss.Width` + `wrapPreservingGuide` per tick. `renderProgressBlock` is now a no-op (progress renders inline via `renderTurnBody`/`renderLiveIteration`), so the tick path no longer assembles a progress-block section. Scroll behavior (atBottom/GotoBottom/newContentHint) is preserved identically.
- **`syncProgressTodos` must do change detection before calling `relayoutViewport`.** High-frequency progress events carry the same Todos every time. Without `todosEqual()` check, each event triggers `relayoutViewport` → `fullRebuild` → `glamour.Render` + `chroma.Highlight` on ALL messages — ~34% CPU waste during agent work. Only call `relayoutViewport` when todo count changes; for content-only changes (e.g. item marked done), just set `renderCacheValid = false`.
- **`relayoutViewport` only invalidates render caches when width changes.** Height-only changes (todo bar, panel open/close, `endAgentTurn`) just resize the viewport without rebuilding all messages. Without this guard, every `endAgentTurn` / `handleProgressDone` triggers O(N) `fullRebuild` with `glamour.Render` on every message — accounts for ~36% CPU during spike periods.
- **`viewport.SetContent` calls `maxLineWidth` internally which runs `ansi.StringWidth` on every line — ~49% CPU with large content.** `cli_viewport_bypass.go` bypasses this by directly setting viewport's private `lines` and `longestLineWidth` fields via `unsafe` (offsets computed via `reflect.FieldByName` at init). **The caller must pass the REAL measured max width, NOT cw.** Viewport's `visibleLines()` trusts `longestLineWidth <= maxWidth` to skip truncation. If `maxW = cw` but some wrapped lines are actually wider (hardwrap edge cases, glamour output), those lines escape truncation, then lipgloss v2's `Wrap()` in `viewport.View()` re-wraps them, producing extra rendered lines that overflow the viewport height and push the input box off screen. `setViewportContent` tracks actual `maxW` via `lipgloss.Width()` during the wrap loop; `cachedHistoryMaxWidth` caches this for the fast path.

Now created in `cli.go:Start()`. Any new model construction must also set it.
- **`syncProgressTodos` must call `persistTodosToManager()` after updating `m.todos`.** Without this, todos live only in `m.todos` (volatile per-session slice) and are lost on turn end/session switch. The helper converts `[]CLITodoItem` → `[]tools.TodoItem` and calls `SetTodos` on the CLI-side TodoManager. `saveCurrentSession()` later calls `SaveToFile` for disk persistence.
- **`/su` and `/chat` commands MUST call `saveCurrentSession()` before changing `m.chatID`.** They were directly mutating identifiers without saving the old session's state (typing, progress, messageQueue, inputDraft) — permanent data loss on session switch. Now also reset critical fields (`typing`, `progress`, `inputReady`, `tickGen++`, etc.) after switching, mirroring `postRestoreSessionSetup`.
- **`syncProgressTodos` MUST NOT clear `m.todos` when `payload.Todos` is empty.** An empty `Todos` field only means "this progress event carries no todo data" (e.g. early thinking phase before `todo_write` executes), NOT "todos were deleted". Clearing on empty caused TODOs to vanish as soon as iteration started. Clear only on: user sending a message (`todosDoneCleared` guard), turn ending with all done (`endAgentTurn`), or explicit `todo_write([])`.

### CLI Race Conditions (Remote Mode Session Switching)
- **`handleSuHistoryLoad` must NOT clear `suLoading` before the stale check.** The old code set `m.suLoading = false` unconditionally on line 876, BEFORE checking `msg.chatID != m.chatID`. A stale RPC callback from the old session clears the new session's loading guard, letting progress events through prematurely and corrupting typing/idle state. The `suLoading=false` now only executes after the stale guard passes.
- **`handleHistoryReload` needs `channelName`/`chatID` stale check.** `cliHistoryReloadMsg` had no session identifiers — an old session's async history load could overwrite `m.messages` after the user already switched away. Added `channelName`/`chatID` fields to the message and a guard in the handler.
- **`splashTickMsg` must carry `gen` (tickGen) for stale rejection.** Rapid session switching creates multiple splash tick chains. Without gen checking, old ticks from cancelled sessions compete with new ticks, causing animation jitter and potential state corruption. Handler now returns early when `msg.gen != m.tickGen`.
- **`handleSuHistoryLoad` default branch does NOT restore `lastTokenUsage` — context bar shows 0 on first switch to idle session.** The `acceptProgress` branch restores token usage from `activeProgress.TokenUsage`, but when the target session has no active turn, the `default` branch runs and leaves `lastTokenUsage` nil. Fix: `suLoadHistoryCmd` now fetches token state via `GetTokenStateFn` and `suHistoryLoadMsg` carries `tokenPrompt`/`tokenCompletion`; the handler falls back to this when `lastTokenUsage` is still nil after processing.
- **Remote reconnect handler must NOT SetProcessing(true) when progress.Phase == "done".** `GetActiveProgress` may return a stale snapshot whose Phase is already "done" (server hasn't cleaned it up yet). Calling `SetProcessing(true)` on a done turn causes the TUI to start a new empty turn (spinner + streaming slot) with no further progress events arriving — permanent spinner. Fix: only `SetProcessing(true)` when `progress != nil && progress.Phase != "done"`.

### TUI Control & Config Tools (AI-Native)
- **`SyncLayoutSettings` and 5s polling goroutine REMOVED.** Layout sync is now event-driven: `ApplyInitialLayout` at startup, `doSaveSettings` → `cliSettingsSavedMsg` for user changes, `tui_control` for AI changes. `refreshRemoteValuesCache` runs ONCE at startup, not every 5s. `valuesCache` is updated on-demand by settings panel save, subscription switch, and config tool set callbacks. Adding polling back will cause ~30% CPU waste from unnecessary `invalidateAllCache` → `fullRebuild` cycles (7+ GB/min temporary string allocations observed).
- **`relayoutViewport` → `newGlamourRenderer(cw - 4)` must only be called from the event loop goroutine.** The glamour renderer is NOT goroutine-safe. Background goroutine calls cause concurrent access to `m.renderer` and crash.
- **`sidebar_width` and other layout keys are NOT in `config.Config` struct.** `SaveToFile` deep merge only PRESERVES unknown keys from disk, never writes new ones. Use `saveLayoutToConfig()` (raw JSON read-modify-write) to persist these keys to `config.json`.
- **Remote `tui_control` flow**: Server → `tui_control_req` WS message → client `readPump` → `tuiControlReqCb` → `SendTUIControl` → `asyncCh` → `handleAsyncDrain` → `program.Send` → event loop → `handleSessionControlMsg`. The WS callback in `transport_remote.go` MUST be wrapped in `go func()` to keep `readPump` responsive — otherwise RPC calls within handlers (e.g. `SessionsDeleteFn`) deadlock waiting for responses.
- **`config` tool uses `SettingsSvc` auto-injection, not Agent callbacks.** `buildToolContext` injects `ConfigGet`/`ConfigSet` from `cfg.SettingsSvc`. Runner CRUD callbacks (`RunnerCreate`/`RunnerList`/`RunnerDelete`/`RunnerGetActive`/`RunnerSetActive`/`RunnerRename`) are injected from `tools.RunnerTokenStore` via `tools.GetRunnerTokenDB()`. Works in ALL modes (local + remote via RPC). Do NOT rely on Agent `SetTUICallbacks` for config.
- **Runner switch is session-level, not user-level.** `config switch` writes to `SandboxRouter.sessionRunners` (in-memory sync.Map keyed by `"channel:chatID"`). Per-tool-call re-resolution in both `buildToolExecutor` (engine_wire.go) and `defaultToolExecutor` (engine.go) calls `SandboxForSession` before each Execute. All tools (Shell, Read, Grep, Glob, FileReplace) immediately route to the new runner. CWD auto-resets to runner's live workspace.
- **`config` tool masks sensitive keys on read** (`api_key` → `sk-a***`, `runner_token` → first 4 chars + `***`). Writes are NOT blocked — users can type API keys anyway, our responsibility ends at masking.
- **⛔ `tui_control` 是 **CLI 渠道专属工具**（用户 2026-09-20 要求「应该只在 cli 注册」；`agent/agent.go` 用 `registry.RegisterForChannel("cli", &tools.TuiControlTool{})` 而非 `RegisterCore`）。** TUI 只存在于 CLI —— 本地与远程 CLI 的 sessionKey 都是 `cli:...`，都命中该渠道。web/feishu 等渠道既**看不到**（`AsDefinitionsForSession` 按 sessionKey 的 channel 前缀取 `channelTools`）也**执行不了**（`GetForSession` 回落全局查找 ⇒ 不存在）。⚠️ web 端浏览 CLI 会话时 `physical_channel` override 把 sessionKey 换成 `web:...`（`agent/engine_wire.go`），同样过滤掉 —— 与"web 里没有 TUI"一致。历史 bug：全局注册 ⇒ web/feishu 会话能看到它（提示词还引导模型去调用），调用必然报 "only available in local CLI mode"（用户实测：web 里让它改会话名 → 报这个错）。**SubAgent 不继承**：channel 工具会随 `Registry.Clone()` 进子代理注册表，而 `filterSubAgentTools` 只遍历全局工具（删不掉 channel 工具）⇒ `buildSubAgentRunConfig` 显式 `subTools.UnregisterChannelTool("cli", "tui_control")`（子代理绝不能切换/关闭用户正在看的会话）。测试：`agent/tui_control_channel_test.go`（cli 可见/可执行 + web/feishu/空 key 不可见/不可执行 + 无全局注册；子代理注册表不含该 channel 工具、带渠道前缀的 key 也查不到）。
- **`DeleteTenant`/other `TenantService` methods must nil-guard `s.db`.** Interactive session cleanup races with DB initialization — `destroyInteractiveSession` can fire before the DB is connected, causing nil pointer dereference.

### SubAgent Progress Identity
- **All SubAgent progress structs MUST carry an `Instance` field** (`CLISubAgent`, `WsSubAgent`, `SubAgentNode`, `childAgentStatus`). `mergeSubAgentTrees` uses `Role + ":" + Instance` as the unique key — without Instance, same-role different-instance SubAgents collapse into a single tree node.
- **`RunSubAgent` interface must include `instance` parameter.** One-shot SubAgent goes through `spawnAgentAdapter.RunSubAgent` → `buildMsg` → metadata. Without this, instance never reaches `SubAgentProgressDetail` and the progress tree can't distinguish parallel SubAgents.
- **`isPlausibleAgentRole` must strip `[instance]` suffix before the space check.** The formatted line `"> 🔄 explore [mem-1]: desc"` has `"explore [mem-1]"` as the role candidate, which contains a space and would be rejected. Strip `[instance]` before `strings.Contains(name, " ")` — otherwise ALL SubAgent progress lines with instance are filtered out by `isStatusEmojiLine`.

### Reasoning Contamination
- **`mergeProgressState` replaces whole-replacement + carryForward.** Structured progress events merge field-by-field into `progressState.current` (in-place), preserving stream-only fields (`StreamContent`, `ReasoningStreamContent`, `StreamingTools`, `StreamTokens`). On iteration change, stream fields are cleared. This eliminates `carryForwardProgressState` (9 fields), `reasoningByIter`, `lastReasoning`, `lastCompletedTools`, and all their fallback chains. `StreamingTools` are filtered against `ActiveTools` names — when a tool transitions from "generating" to "running", the stale generating entry is removed (prevents "preparing…" persisting alongside "running").
- **`snapshotIterationChange` reads directly from prev (pre-merge shallow copy).** `mergeProgressState` updates in-place, so `handleProgressMsg` shallow-copies `current` into `prev` BEFORE merging. Snapshot reads `prev.Reasoning` → `prev.ReasoningStreamContent` (2-level, no `reasoningByIter`/`lastReasoning`). No `lastCompletedTools` — CompletedTools come from `prev` directly.
- **Ctrl+C cancel path captures streamed content as snapshot fallback.** When Ctrl+C interrupts mid-stream, structured fields are empty. The streamed content in `prev` (pre-merge copy) or `m.progressState.current` is the only data available. Priority: `prev.Reasoning` → `prev.ReasoningStreamContent` → `msg.payload.Reasoning` for reasoning; `prev.Thinking` → `prev.StreamContent` for content. `handleCancelAck` MUST call `updateViewportContent()` after `rerenderCachedMessage()` — without it, the viewport shows stale streaming content until the next 100ms tick (visually: "history disappears then re-renders").
- **`handleSuHistoryLoad` acceptProgress assistant merge must NOT cross turns.** When TUI restarts mid-turn, the code merges the last history assistant into `startAgentTurn()`'s empty streaming slot. The old code searched backward for `role=="assistant"` and always merged — but if there's a `role=="user"` message between the found assistant and the streaming slot, the assistant belongs to a PREVIOUS turn. Merging it displays the previous turn's content as the current streaming message (Bug: stale content appears below latest iteration on restart). Both merge branches (the `canMerge` path and the `streamingMsgIdx < 0` path) must scan for intervening user messages before merging.
- **`StreamingTools` is a stream-only field — same protection rules as `StreamContent`/`ReasoningStreamContent`.** It carries tool names detected during LLM streaming (Status="generating"), before arguments finish generating. Must NEVER enter `snapshotIterationChange` or any structured snapshot path. `isStreamOnly` must check `len(StreamingTools) > 0` and merge into `current.StreamingTools`. `CollectStreamWithCallback` now has 5 params (added `onToolCall func([]ToolCallDelta)`) — fires once per tool name arrival (first chunk), NOT per argument delta. `GenerateStreamAndCollect` and `generateResponse` signatures also gained the matching param. `buildStreamCallbacks` returns a third callback that converts deltas to `[]ToolProgress{Status:"generating"}` and broadcasts via `SendProgress` (not `SendStreamContent`, which only supports content/reasoning strings).
- **`buildStreamCallbacks` only broadcasts to the ORIGINATING channel.** Each channel's `SendProgress` already broadcasts to ALL Hub subscribers (including other channels' clients via the shared Hub). Broadcasting to multiple channels causes duplicate delivery: each subscriber receives the same event N times (N = number of ProgressSender channels). This was the root cause of the "two consecutive Assistant messages" bug that only appeared when Web and TUI were both open on the same session — duplicate stream events arrived after state transitions, triggering `startAgentTurn` to create a duplicate streaming assistant.

### Backend/Transport Architecture
- **AgentChannel processing loop MUST be concurrent (each request in its own goroutine).** The old serial processing loop (`case req := <-ac.inbox: runFn(...)`) caused circular-wait deadlocks when two agents SendMessage to each other — A's runFn blocks waiting for B's reply, but B's inbox can't be processed because A's loop is stuck in runFn. Fix: dispatch each request to `ac.wg.Go(func() { processRequest(req) })`.
- **AgentChannel.Send() MUST respect caller context via `msg.Ctx`.** `OutboundMsg.Ctx` (json:"-") carries the caller's context so `Send()` can detect Ctrl+C/tool-timeout. Without this, `Send()` only checks `ac.ctx.Done()` (from `context.Background()`), making Ctrl+C unable to unblock pending RPCs. `Dispatcher.SendMessageCtx(ctx, ...)` sets `OutboundMsg.Ctx`. `MessageSenderCtx` interface extends `MessageSender` with context-aware sending. `sendMessageWithCtx()` in send_message.go uses type assertion to prefer `MessageSenderCtx`.
- **AgentChannel.StartWithContext(parentCtx) binds lifecycle to parent.** When the parent agent is cancelled (Ctrl+C → `agentCtx` cancelled → `Agent.Close()`), all AgentChannels stop. Use this for agent-owned channels instead of plain `Start()`.
- **`registerAgentChannel` callback creates AgentChannel with `Start()`.** For parent-context binding, use `StartWithContext(agent.agentCtx)` — but note `agentCtx` is only set during `Run()`. Current code uses `Start()` and relies on `Dispatcher.Stop()` during shutdown to clean up. The caller-context cancellation via `msg.Ctx` is the primary Ctrl+C propagation mechanism.
- **CLI always uses Client → Transport → Server, even in local mode.** Client (agent/client.go) is a pure RPC client — every method is `Transport.Call("method", params)`.
- **Transport is the pure transmission layer** (agent/transport.go). Only 2 methods: `Call(method, payload)` and `Close()`. `ChannelTransport` (agent/transport_channel.go) dispatches directly to `ServerCore.HandleRPC`. `RemoteTransport` (agent/transport_remote.go) sends JSON-RPC over WebSocket.
- **`connect()` replaces `t.conn` with a new WebSocket — old `readPump` must NOT clear the new connection.** Old `readPump` hits `ReadMessage` error after `old.Close()`, then unconditionally sets `t.conn = nil` and fires a second reconnect — causing an infinite reconnect loop, dropped `BindChat`, and permanent spinner. Fix: `readPump` checks `t.conn == conn` before clearing; if `connect()` already replaced the connection, old `readPump` returns silently without clearing or signalling.
- **`setConnState` must NEVER be called while holding `t.connMu`.** `setConnState` internally acquires `t.connMu.Lock()`. Go `sync.Mutex` is NOT reentrant — calling it inside the same-goroutine `connMu` critical section deadlocks the entire event loop (TUI frozen, Ctrl+Z broken). Fix: set a local flag inside the lock, call `setConnState` after `Unlock()`.
- **`RemoteTransport` events (conn_state, reconnect) must bridge to `Client`'s subscriber base.** `RemoteTransport` and `Client` each create their own `baseTransport` instance. Events emitted by `setConnState`/`reconnectLoop` on `RemoteTransport.baseTransport` never reach subscribers registered via `app.client.Subscribe()` (which uses `Client.base`). Fix: `Client.Start()` calls `ShareEventBase(&c.base)` on the transport; `RemoteTransport.emitLocal()` dispatches on the shared base. Any new local event in RemoteTransport must use `emitLocal`, not `t.emit()`.
- **Disconnect detection must cover write failures, not just read errors. And the TUI must react immediately.** Fix: (1) transport: `sendPing`/`SendMessage` clear `t.conn` on write failure. (2) TUI: `sendInbound()` immediately sets `m.connState = "disconnected"` when write fails. **CRITICAL: The `sendInboundFn` callback in main.go was fire-and-forget (`clipanic.Go` goroutine) and ALWAYS returned `true` — making ALL TUI-layer checks dead code. Every `sendInbound`/`sendMessage`/`sendToAgent` fix was unreachable because the callback never reported failures. Fix: `sendInboundFn` must call `SendInbound` synchronously and return the real result. Also: `sendMessage()` (main path from handleEnterKey) AND `sendToAgent()` (slash commands) both check return value before `startAgentTurn()`. (3) View() reconnect overlay must come BEFORE `suLoading` — stale `suLoading` from a dead server permanently blocks the splash.**
- **FINAL ARCHITECTURE: `showDisconnect` removed — `connState` is the single source of truth.** All splash, disconnect guard, and tick conditions use only `m.connState`. `SetConnState` writes `connState` directly to model (bypasses all channels). `sendInboundFn` is async (`clipanic.Go`) and does NOT touch `connState` — transport layer manages state independently. `handleSuHistoryLoad` skips redundant RPC when history already provided in message. **`readPump` must start BEFORE `emitLocal(ReconnectEvent{})`** — otherwise `BindChat`/`GetHistory` RPCs in the handler have no reader and timeout after 30s, freezing the TUI. No deadlocks, no race conditions, no redundant flags.
- **ServerCore** (serverapp/server_core.go) is the shared server core for both local and remote modes. Owns Agent + RPCTable + Dispatcher + Bus. Created by CLI (local mode) and server.go (remote mode).
- **RPCTable is the single handler truth source** (serverapp/rpc_table.go). Handlers access `h.Ag` (the *Agent) directly — no intermediate Backend/DirectBackend layer.
- **Lifecycle interfaces** (agent/lifecycle.go): AgentRunner, EventRouter, CallbackRegistry — only used by the legacy Backend struct for remote mode.
- **Adding a new RPC method**: 1 handler in rpc_table.go (using h.Ag) + 1 method in client.go (Transport.Call) + 1 MethodXxx constant in req_types.go.
- **Adding new transports** (gRPC, MCP) only requires implementing 2 Transport methods (Call + Close).
- **ChannelPluginTransport (`agent/transport_channel_plugin.go`) is a separate concept from Transport.** It wraps a channel plugin process's stdin/stdout as a bidirectional JSON-RPC channel (not an agent Transport). The plugin acts as a full RPC client (like remote CLI over WS). Created by `stdioChannelPluginProvider` (`serverapp/channel_plugin.go`) which spawns a **dedicated** process — NOT the same process used for plugin activation.
- **`ChannelProviderFactory` replaces the old `GrpcChannelBridgeFactory`.** Defined in `plugin/channel_provider.go`. The factory is set by serverapp during init with a lazy RPCTable reference (plugins activate during `InitServer` before RPCTable exists).
