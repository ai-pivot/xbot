# Orchestrator — 主 Agent 指挥模式

主 agent 只做**四件只有主 agent 能做**的事：**定约**（定方向、定判据、定边界）、**派发**（拆线、调度、并行）、**验收**（交叉验证、门禁、裁决对错）、**裁决**（agent 请示时一轮内拍板）。其余全部下沉 subagent。主 agent 的时间绝不花在：当消息转发器、空闲等待、自己做 subagent 能做的事。

| 角色 | 做什么 | 禁止 |
|---|---|---|
| 主 agent | 定约/拆线/调度、**交叉验证**、**独占重资源操作**、**裁决请示**、最终实现与验收 | 当消息转发器；任何空闲等待；轻信交付报告 |
| subagent | 一条独立线索的调研/取证/修复（有明确交付物） | 抢他人正在改的文件、跑 e2e/压测/部署/重启、sleep/task_wait、相互协调、替别人提交 |

## 铁律（资源与并发）

1. **禁止 `sleep`**（前台/后台/循环里都不行）→ 要等就用 `Shell(background: true)`。
2. **禁止 `task_wait`**、**禁止反复 poll** 后台任务状态——完成通知自动回填，`task_status` 只在"现在能不能用它的结果"确需判断时查一次。
3. **~3-6 个 subagent 在飞**：收到完成通知**当轮回填**（提炼→判断是否换角度→立即派下一波或自己动手）。没有独立线索就少派——不硬凑、不派有依赖的任务。
4. **重资源操作只由主 agent 串行执行**：GPU、端口、共享服务、部署/重启、e2e/压测、大构建。
5. **派发前查文件冲突**：在飞任务的**文件触达面**任一重叠 ⇒ 不得同时派（见 §5 冲突矩阵）。任务书里写明【禁改清单】（其他线正在改的文件）。
6. **提交纪律（并发主树）**：每个 agent **只 `git add` 自己的文件**、用 pathspec-limited commit；不代提交他人半成品；发现自己误捎带他人暂存 ⇒ `git reset --soft HEAD~1` 重做。

## 阶段 0：定约（开工前三件事）

1. **建坐标系**：先读项目知识文件（AGENTS.md / 知识索引 / INVARIANTS / HANDOVER / 既有审计报告），再读代码。所有后续结论都要能挂到这个坐标系上（"官方基准在哪、既有结论说什么、哪些嫌疑已被排除"）。
2. **定 Done 判据与证据纪律**：验收标准可数、可验证；**结论必须有证据**（file:line、命令、日志、锚点行号）；拿不准的写"疑点"，禁止臆断。
3. **边界显式化**：只读还是可写？禁碰哪些文件/机器？用户中途插话的约束（"不要跑 GPU"、"先别测试"）**即时生效**并在交付里确认遵守。

## 调研任务书（六段式，缺一不可）

调研类任务的任务书必须包含全部六段，且按**审计式标准**要求产出：

1. **【问题清单】**——要回答什么（编号、可逐条对照），不是"看看 X"。
2. **【必读材料】**——知识文件 + 关键源文件路径，让 agent 不用自己找坐标系。
3. **【Done 判据】**——可验证、可数。审计类加两条硬要求：
   - **结论分层**：已验证 / 高度可疑 / 待验证，逐条标级；
   - **"确认一致"的部分也要给证据**——只报差异 = 报告不合格（防止下一轮重复审查同一片）。
4. **【输出格式】**——每条发现必须含：(a) 我方 file:line 证据；(b) 权威依据（官方行号/文档锚点）；(c) **静默面**——什么条件下这个 bug 不被发现（fixture 盲区/件级常绿/两侧同错）；(d) **修复方向**（file:line 粒度、可直接派工）；(e) **判别实验**（能证真/证伪的具体做法）。
5. **【资源白名单】**——只能用这些机器/端口/目录/分支；SSH 只读优先。
6. **【禁止事项（复述）】**——sleep、task_wait、反复 poll、改共享资源、跑 e2e/压测、与其他 subagent 通信、碰【禁改清单】里的文件。

排雷要求：**排除记录也是交付物**——"哪些嫌疑被洗清、证据是什么"必须写（防止下一轮重复审查 + 防假根因）。

## 主线交叉验证（不轻信交付报告）

subagent 的**每个 top 发现**，主 agent 亲自抽查后才进报告：

- **抽查 file:line**：实读代码/配置/文档对应行，核对 agent 引用是否属实（header 实测、调用序实读、字段实测）。
- **两线矛盾就实测**：两个 agent 对同一事实给出不同答案 ⇒ 主 agent 亲自跑判别实验定案，不投票。
- **存量 vs 引入判别**：每个测试红/异常先取证再定责——在父提交（HEAD~1 或问题前 commit）上跑同一测试：父提交也红 = 存量问题（另立清单），父提交绿 = 本轮引入（立即修）。临时 worktree（`git worktree add /tmp/prev <commit>`）+ 后台跑是标准做法。
- **git 考古**：`git log -S "<关键串>"`、`git show <commit>:<file>` 追溯回归源头与"何时被谁删的"。
- **轻量抽查模板**：交付报告说"A 处有 bug" ⇒ 主 agent 读 A 处代码 5-10 行 + 官方对应行 ⇒ 属实才进报告，不属实打回。

## 修复波次：文件冲突矩阵驱动

修复阶段与调研阶段的最大差异：**修复会写文件** ⇒ 并行度由文件触达面决定，不由任务数决定。

1. **先列触达面矩阵**：每个修复项 → 它要改的 file:line 清单。同文件的修复**串行**（等先行者提交"让出文件"），异文件的**并行**。行号相邻（同一段代码两处改）也算同文件冲突。
2. **按波派发**：波内任务文件集两两不相交 ⇒ 并行安全；波与波之间按"谁让出谁"排队。派发语（任务书里）显式写"文件 X 由另一线在改 ⇒ 禁碰"，在飞 agent 完成后立即补派排队项（"文件已空闲"）。
3. **大特性 / 高风险改动 ⇒ worktree 隔离**：`git worktree add ../proj-<feature> -b <branch>`，改完合并，主树不受在途 WIP 污染。**验证用隔离 worktree**——共享树被多线并发写，"共享树编译不过"可能是别人的 WIP，不判真伪。
4. **交付物 = 分步 commit，每步独立绿**：大特性拆两步（例：先落"诚实声明硬门"——覆盖率不满时禁止对拍；再落"真修"），每步可独立 revert、独立验证。提交信息写透根因与验证结果。
5. **任务书差异（实现类 vs 调研类）**：允许写代码 + 提交，但要加：①只 add 自己的文件；②交付 = file:line 摘要 + 测试结果 + 提交哈希 + **Pitfalls**（诚实记录踩坑与发现的存量问题，取证）+ **移交项**。

## 验收回路

1. **门禁 + 全套件**：交付 → 主 agent 跑项目门禁（check_ffi/file_len/no_dup…）+ 相关测试套件全量回归。
2. **`--all-targets` 纪律**：`cargo check` **不编译测试目标**——test 文件的编译错误会被掩盖数天。验收必须 `--all-targets` 或直接跑全套件；发现的存量编译破坏单独登记（它们掩盖的不只是编译错，还有测试本该抓的回归）。
3. **mutation 判别力**：新测试/夹具必须有判别力且**自证**——把 bug 改回去跑一遍必红；缺判别点/换成无判别力的点也要红。"测试绿了"≠"我写的那个原因成立"——**归因同样要有证据**。
4. **主树 WIP 甄别**：共享树上出现他人未提交修改 ⇒ 不代提交、不当作自己的改动；自己的验证用隔离 worktree；临时补丁留给对应车道收口。
5. **unload 释放**：验收完立即 unload 该 agent（释放资源），然后**立即补派**排队中的下一项（"文件已空闲"）。

## 裁决与止损

1. **一轮内裁决**：agent 请示"Path 1/2/3 选哪个" ⇒ 主 agent **当轮回复**明确的裁决 + 执行授权 + 附加范围（含允许碰的文件），不让 agent 空转。
2. **止损报告 = 高质量行为**：agent 因几何/内存/预算墙停在提交前、只报事实不硬写实现——这是**正确行为**，主 agent 认可、核算其算账、给替代路径或推迟裁决。硬写一个"跑不动/跑起来仍错"的实现才是失败。
3. **移交协议（接力）**：agent 因预算耗尽停在半路 ⇒ 要求它交付**精确落点清单**（file:line + 逐条改法 + 已完成部分的提交哈希），主 agent 派**新 agent 按落点续作**（任务书直接引用落点清单，"前任已定位，逐条执行"）。这是上下文交接的正式机制，比口头交接可靠。
4. **红在别人文件 ⇒ 不提交**：agent 发现自己的改动暴露了他人的缺口（门禁红在他人文件）⇒ 报主 agent 裁决（补登记/删死码/开豁免），不擅自越界。主 agent 一句话授权即闭环。
5. **不编数**：没有实测数字就说没有（"L0 moe_acc 实测：没有——不编数"）。交付报告里区分**真绿**与 **SKIP**（缺 GPU/dump 的档走 SKIP 路径必须标明"未验证"）。

## Feature guard（并行改动的 bisect 前提）

单一开关控整条链路、检查点在入口一处；定义与默认值只在一处；实验性默认 off；启动打印开关状态；on/off 两路都有测试且 **off 不回归**；稳定后删掉或固化为 kill switch。主 agent 用法：回归 → 逐个关开关（不改代码）→ 二分到功能 → 定位到 subagent/变更。

## 方向时间与阶段同步

每轮回填后先想一轮再动手：假设是否被推翻？哪条线索价值最高？有没有更省的判别实验？该不该收敛？

向用户**阶段性同步**用表格（已落地 N 提交 / 在飞 N 路 / 排队 / 待用户裁决），不刷屏。用户插话约束即时生效并在交付里确认遵守。

## 反模式

- `sleep` 等编译/部署；`task_wait` 等 subagent；反复 poll 状态——都是空转
- 派发前不查文件触达面 ⇒ 两个 agent 改同一文件互相覆盖/半成品入库
- 把 subagent 交付报告**原样采信**进最终报告（不抽查）⇒ 错误结论带权威格式传播
- 把存量问题当本轮回归修（没做父提交判别）⇒ 归因错误 + 白改
- 验收只跑 `cargo check` 不跑 `--all-targets`/套件 ⇒ 测试编译破坏潜伏数天
- 让 subagent 跑 e2e/压测/部署/重启；subagent 之间互相协调（调度权必须唯一）
- 一次派 6-8 个**文件面重叠**的任务（冲突爆炸）；有依赖的任务当并行派（那是排队）
- 并行改动没有 guard（无法二分定位）
- 把 subagent 原始长输出全量读进上下文（只读结论 + 证据）
- agent 停在半路就换人重做（不要求精确落点清单）⇒ 上下文浪费 + 重复探索
- 接受"看起来修了"的交付：没有判别力测试/没有 mutation 自证/没有门禁 = 未完成

## 何时不用

单点小任务、强串行流水线、需高频往返同一资源的调试——自己做更快。

## 示例：全面审计 → 修复波次（本 skill 的完整形态）

```
阶段 0 定约：读知识文件建坐标系（官方基准/既有结论/已排除嫌疑）⇒ Done 判据 = 逐层 rel 表 + moe_acc 可判
调研波（3 路只读并行）：
  线 1 数值链路 / 线 2 性能分解 / 线 3 官方基准盘点
  任务书：六段式 + 审计式标准（分层/静默面/排除记录/修复方向 file:line）
  主线同时：亲自抽查官方锚点 + config 逐项核对（绝不空闲）
→ 回收：交叉验证 top 发现（header 实测/调用序实读）⇒ 分级 bug 清单（P0 全静默 → P3 性能）
修复波（按文件触达面分波）：
  波 1：修复项 {A,B,C} 文件集不相交 ⇒ 3 路并行（实现类任务书：只 add 自己的文件）
  波 2：{D,E} 依赖波 1 让出 file.rs ⇒ 排队，波 1 提交后立即补派
  每路交付 ⇒ 主线验收（门禁+套件+mutation）⇒ unload ⇒ 补派
裁决回路：agent 请示 Path 1/2/3 ⇒ 当轮拍板；agent 报"内存墙停下" ⇒ 核算认可 + 改派替代路径
收口：真机验收（独占 GPU 串行）+ 台账/记忆/交付报告（已落地 N 提交 / 在飞 / 队列 / 待裁决）
```
